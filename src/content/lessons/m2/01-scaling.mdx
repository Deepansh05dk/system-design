<Callout type="problem">
Your app runs on one server. Traffic doubles every month. The CPU is at 95% at peak and pages are timing out. You have two options: **buy a bigger server**, or **add more servers**. Which one, and what has to change in your code for the second one to work?
</Callout>

## Two ways to scale

- <Term k="vertical-scaling">**Vertical scaling (scale up)**</Term>: replace the machine with a bigger one: more CPU, more RAM, faster disk.
- <Term k="horizontal-scaling">**Horizontal scaling (scale out)**</Term>: add more machines and split the work between them.

## The key to scaling out: stateless servers

Imagine a user logs in and their session is stored **in the memory of Server 1**. The next request goes to Server 2, which has no idea who they are. They're logged out!

A <Term k="stateless">stateless</Term> server keeps **no user-specific data in its own memory between requests**. Any state is moved to a shared place:

<Callout type="analogy">
A stateless server is like a bank teller who looks up your account on the central system. You can go to **any** counter. A stateful server is a teller who keeps your file in their own drawer. You must wait for **that** teller, and if they go home sick, your file is stuck.
</Callout>

<Callout type="frontend">
This is the same idea as keeping React components pure and putting shared state in a store (Redux, Zustand) or on the server. Components that don't hold hidden state are easy to reuse and replace. Servers too.
</Callout>

## Sticky sessions: a shortcut with a cost

Some load balancers support **sticky sessions** (session affinity): the same user always goes to the same server, usually via a cookie. This lets stateful apps scale a bit, but:
- load becomes uneven (some servers get the heavy users),
- when a server dies, its users lose their sessions,
- scaling down is harder.

Prefer stateless servers; use stickiness only where it's truly needed (e.g. a WebSocket connection naturally stays on one server).

## Auto-scaling

With stateless servers in the cloud, you can **auto-scale**: add servers when CPU > 70% or request rate rises, remove them when it falls. You pay for what you use. Keep a minimum count across multiple **availability zones** (separate data centers) so one zone failing doesn't take you down.

<Callout type="interview">
Start simple and evolve out loud: "We start with a single server. To scale, first I make the app servers **stateless** (sessions in Redis, files in S3), then put them behind a **load balancer** with auto-scaling. The database scales separately: first vertically, then read replicas, then sharding if writes demand it." This narrative is exactly what interviewers want to hear.
</Callout>

<Takeaways>
- **Vertical** = bigger machine: simple, but limited, costly and a single point of failure.
- **Horizontal** = more machines: scalable and resilient, but needs a load balancer and **stateless** servers.
- Move state to shared stores: **sessions → Redis/JWT, data → DB, files → object storage**.
- In practice: app servers scale **horizontally**; databases often start **vertical**, then replicas and shards.
</Takeaways>
