<Callout type="problem">
When a user uploads a video, your API must: save the file, transcode it to 5 resolutions (10 minutes!), generate thumbnails, update the search index, and notify 2 million subscribers. If the API does all this before responding, the user stares at a spinner for 10 minutes, and if any step fails, the whole upload fails. **What if the API just said "Got it!" and the work happened in the background?**
</Callout>

## The idea: decouple with a queue

A <Term k="queue">message queue</Term> is a buffer between the code that **creates** work (**producers**) and the code that **does** work (**consumers / workers**):

1. The API puts a message in the queue: `{ "type": "video_uploaded", "videoId": 991 }`.
2. It immediately responds to the user: "Upload received, processing…".
3. Workers pull messages from the queue and do the heavy work at their own pace.

## What queues give you

- **Faster responses:** users don't wait for slow work.
- **Load leveling:** a spike of 10,000 jobs/sec doesn't crash workers; the queue absorbs it and workers drain it steadily.
- **Decoupling:** the producer doesn't know or care who consumes. Add a new consumer (e.g. analytics) without touching the producer.
- **Reliability:** if a worker crashes, the unacknowledged message goes back to the queue and another worker picks it up.
- **Independent scaling:** scale workers based on queue length.

<Callout type="analogy">
A restaurant. Waiters (API servers) take orders and pin tickets on a rail (the queue). Cooks (workers) take tickets when they're free. A rush of customers doesn't make the waiters cook; tickets just pile up a bit and the kitchen catches up. Hire more cooks if the rail is always full.
</Callout>

## Kafka: the log that everyone uses

<Term k="kafka">Apache Kafka</Term> is not a classic queue. It's a **distributed, append-only log**:

- Messages are **appended** to a topic and **kept** for days (or forever), not deleted when read.
- A topic is split into **partitions** for parallelism. Messages with the same **key** (e.g. `user_id`) always go to the same partition, so their **order is preserved**.
- Each consumer group tracks its own **offset** (position in the log). Different groups read independently; a new consumer can even **replay** history from the start.
- Very high throughput (millions of messages/sec across a cluster), because it writes sequentially to disk.

## Delivery guarantees

| Guarantee | Meaning | Risk |
|---|---|---|
| **At most once** | Delivered 0 or 1 times | Messages can be lost |
| **At least once** | Delivered 1 or more times | **Duplicates** possible (most common default) |
| **Exactly once** | Effectively processed once | Hard; needs special support plus idempotent consumers |

At-least-once happens because: a worker processes a message, then crashes **before acknowledging** it. The queue gives the message to another worker, so it's processed twice. That's why consumers should be <Term k="idempotent">**idempotent**</Term>: processing the same message twice has the same effect as once (e.g. "set status = shipped" instead of "add ₹100"; or record processed message IDs and skip duplicates). More in Module 3.

## Failures: retries and dead-letter queues

If a message keeps failing (bad data, a bug), retrying forever blocks the queue ("poison message"). Standard approach:
1. Retry a few times with **backoff**.
2. Then move it to a <Term k="dead-letter-queue">**dead-letter queue (DLQ)**</Term> for humans to inspect.
3. Alert when the DLQ isn't empty.

## Back-pressure

If producers are **always** faster than consumers, the queue grows forever: memory/disk fills, and messages wait hours. A queue absorbs **spikes**, not a permanent mismatch. Watch **queue depth** and **message age**, auto-scale consumers, and if needed, slow producers down (reject or rate-limit at the edge).

<Callout type="interview">
Reach for a queue whenever you hear: "slow", "send notifications", "process upload", "spiky traffic", "multiple services react to one event". Say: "The API writes the order and publishes an `order_placed` event to **Kafka**; email, inventory and analytics consume it independently. Delivery is **at-least-once**, so consumers are **idempotent**. Failed messages go to a **DLQ**."
</Callout>

<Takeaways>
- Queues **decouple** producers and consumers, **level load spikes** and enable **async** processing.
- **Work queue** = each message to one worker. **Pub/sub** = each subscriber gets a copy.
- **Kafka** is a durable, partitioned, replayable log with ordering per key.
- Most systems are **at-least-once** → make consumers **idempotent**.
- Use **retries with backoff + DLQ**; monitor **queue depth** for back-pressure.
</Takeaways>
