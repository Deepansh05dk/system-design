<Callout type="problem">
Your single database handles all reads and writes. Two problems: (1) reads are 95% of traffic and the DB CPU is maxed, and (2) if the disk dies at 3 AM, **all your data is gone**. One idea solves both: keep **copies**.
</Callout>

<Term k="replication">Replication</Term> means keeping the same data on multiple machines (**replicas**). It gives you:
- **Durability:** a disk can die without losing data.
- **Availability:** if one machine fails, another takes over.
- **Read scaling:** spread reads across many copies.
- **Lower latency:** a replica near users in another region.

## Leader–follower (primary–replica)

The most common setup. One <Term k="leader">leader</Term> accepts **all writes**. Followers receive a stream of changes from the leader (usually its write-ahead log) and apply them. Reads can go to any follower.

## Sync vs async replication, and replication lag

<Term k="replication-lag">Replication lag</Term> is usually milliseconds, but under heavy load or across regions it can be seconds or more.

### Problems caused by lag (and fixes)

- **Read-your-own-writes:** a user updates their profile, refreshes, and sees the **old** profile (the read hit a lagging follower). Fix: read **the user's own data** from the leader for a short time after they write, or track the last write position and only read from followers that caught up.
- **Monotonic reads:** a user refreshes and sees a comment, refreshes again and it's gone (different followers, different lag). Fix: route each user to the **same** follower.

<Callout type="frontend">
You've probably seen read-your-own-writes bugs as a user: you post something, the list refreshes, and your post isn't there. A common frontend workaround is **optimistic UI**: show the user's change locally immediately, don't wait for the server read. It hides lag, but the backend fix above makes it actually correct.
</Callout>

## Failover

When the leader dies, a follower must be **promoted**:
1. **Detect** the failure (missed heartbeats, usually a timeout of a few seconds).
2. **Choose** the most up-to-date follower (often via a consensus system, Module 3).
3. **Reconfigure** clients to send writes to the new leader.

Dangers:
- **Lost writes** with async replication (as you saw).
- **Split brain:** the old leader wasn't dead, just slow. It comes back and **both** think they're the leader, both accepting writes. Systems prevent this with **fencing** (the old leader is forcibly blocked) and **epoch/term numbers**.

Managed databases (AWS RDS/Aurora, Cloud SQL) handle failover for you, typically within a minute or less.

## Other replication topologies

| Topology | How | Good for | Hard part |
|---|---|---|---|
| **Leader–follower** | One writer, many readers | Most apps | Write scaling, failover |
| **Multi-leader** | Several leaders (e.g. one per region) accept writes and sync with each other | Multi-region writes, offline apps | **Write conflicts** (two regions edit the same row) |
| **Leaderless** | Write to several replicas, read from several, use quorums (Cassandra, DynamoDB) | High availability, no failover needed | Conflict resolution, tunable consistency |

We'll see quorums and conflicts in "Consistency Models" (Module 3).

<Callout type="interview">
Typical line: "The workload is read-heavy, so I'll add **read replicas** behind the primary. Replication is **async**, so there's some lag; for **read-your-own-writes** (e.g. after editing a profile) we read from the primary. Failover is automatic with a managed database." That covers the usual follow-up questions before they're asked.
</Callout>

<Takeaways>
- Replication = copies on several machines: **durability, availability, read scaling**.
- **Leader–follower**: one writer, many readers. Doesn't scale writes.
- **Async** = fast writes but **lag** and possible data loss on failover. **Sync** = safe but slower.
- Handle lag: **read-your-own-writes from the leader**, sticky follower per user.
- Failover risks: **lost writes** and **split brain**.
</Takeaways>
