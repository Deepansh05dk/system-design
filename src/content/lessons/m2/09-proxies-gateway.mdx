<Callout type="problem">
You have 12 microservices. Every one of them needs to check auth tokens, rate-limit abusive clients, log requests, handle CORS, and terminate TLS. Writing that 12 times in 3 languages is a nightmare. And the mobile app has to know 12 different hostnames. **Where should these shared concerns live?**
</Callout>

## Proxy basics

A **proxy** is a server that sits between two parties and forwards traffic. The difference is **whose side it's on**:

  items={[
    { name: 'Forward proxy', icon: '🧑‍💻→', pros: ['Sits in front of <b>clients</b>', 'Hides the clients from the internet', 'Company firewalls, content filtering, VPN-like privacy, caching for an office'], use: 'Clients choose to use it. The server sees the proxy, not the real client.' },
    { name: 'Reverse proxy', icon: '→🖥️', pros: ['Sits in front of <b>servers</b>', 'Hides the servers from clients', 'Load balancing, TLS termination, caching, compression, routing'], use: 'Servers use it. The client thinks the proxy IS the server. Nginx, HAProxy, Envoy, Traefik.' },
  ]}
/>

A load balancer is a kind of reverse proxy. In system design, "proxy" almost always means <Term k="reverse-proxy">**reverse proxy**</Term>.

## API gateway: a smart reverse proxy for APIs

An <Term k="api-gateway">API gateway</Term> is the single front door for all API calls. It handles **cross-cutting concerns** so services don't have to:

Typical gateway responsibilities:
- **Authentication** (and coarse authorization)
- **Rate limiting & quotas** per user / API key
- **Routing** and API versioning
- **TLS termination**
- **Request aggregation** (one client call → several service calls → one combined response)
- **Observability:** logs, metrics, trace IDs
- **Protocol translation:** e.g. public REST → internal gRPC

Examples: Kong, AWS API Gateway, Apigee, Envoy-based gateways, Nginx.

## Backend for Frontend (BFF)

A variation you'll like as a frontend dev: a **separate gateway per client type**. The mobile BFF returns small, mobile-shaped payloads; the web BFF returns richer data. Each frontend team owns its BFF. GraphQL servers often play this role.

<Callout type="frontend">
If you've written a Next.js API route that calls three backend services and merges the results for one page, you've built a tiny BFF. That's exactly the pattern.
</Callout>

## Watch out

- The gateway is on **every request**, so it must be **fast, horizontally scaled and highly available**. Otherwise it's a single point of failure and a bottleneck.
- Keep **business logic** out of it. Gateways that grow into "god services" become a deployment bottleneck for every team.

<Callout type="interview">
In microservice designs, draw: **Client → CDN → Load balancer → API Gateway → services**. One sentence is enough: "The gateway handles auth, rate limiting and routing, so services focus on business logic." For a monolith, a load balancer/reverse proxy alone is fine. Don't add a gateway just because.
</Callout>

<Takeaways>
- **Forward proxy** = on the client's side. **Reverse proxy** = on the server's side (what we use in designs).
- An **API gateway** is a reverse proxy for APIs: **auth, rate limiting, routing, TLS, logging, aggregation**.
- **BFF:** a gateway tailored per client (web / mobile).
- Keep the gateway **thin, fast and redundant**.
</Takeaways>
