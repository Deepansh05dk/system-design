<Callout type="problem">
You now have 10 stateless app servers. But users only know one address, `api.myapp.com`. **Who decides which server gets each request? What happens when a server crashes at 2 AM?**
</Callout>

A <Term k="load-balancer">load balancer</Term> (LB) sits in front of your servers. Clients talk only to it; it forwards each request to a healthy server.

It gives you three things:
1. **Scalability:** add servers behind it without clients noticing.
2. **Availability:** dead servers are detected and skipped.
3. **A single place** for TLS termination, rate limiting, logging and routing rules.

## Load balancing algorithms

| Algorithm | How it picks | Good for | Weakness |
|---|---|---|---|
| **Round robin** | Each server in turn | Similar servers, similar requests | Ignores how busy a server is |
| **Weighted round robin** | More turns for bigger servers | Mixed server sizes | Still ignores current load |
| **Least connections** | Server with fewest active requests | Requests with very different durations | Needs to track connections |
| **Least response time** | Fastest-responding server | Latency-sensitive apps | More measurement overhead |
| **IP / key hash** | `hash(client or key) % N` | Stickiness, caches per server | Uneven if few heavy clients; reshuffles when N changes |
| **Random / power of two choices** | Pick 2 random servers, use the less busy one | Large fleets, simple and very effective | — |

<Callout type="deep" title="Going deeper: power of two choices">
Picking the least-loaded of **two random** servers gets almost all the benefit of checking every server, without coordinating. It's used by many modern proxies (e.g. Envoy's least-request). A nice detail to drop in an interview.
</Callout>

## Health checks

The LB regularly sends a <Term k="health-check">health check</Term> (e.g. `GET /health` every 5 seconds) to every server. After a few failures in a row, the server is removed from rotation; after a few successes, it's added back.

Notice in the simulator: between the crash and the next health check, some requests still fail. Real systems shorten this gap with **retries** at the LB and **passive health checks** (marking a server bad as soon as real requests fail).

<Callout type="tip">
A good `/health` endpoint checks that the app can actually do its job (e.g. reach its database), not just that the process is running. But don't make it so strict that one slow dependency marks **every** server unhealthy at once!
</Callout>

## L4 vs L7 load balancers (recap)

- **L4 (transport layer):** routes by IP and port. Very fast. Can't see URLs or headers. Example: AWS Network Load Balancer.
- **L7 (application layer):** reads HTTP. Can route `/api/*` to API servers and `/images/*` to image servers, terminate TLS, add headers, do canary releases ("send 5% of traffic to the new version"). Examples: Nginx, HAProxy, Envoy, AWS Application Load Balancer.

## Who balances the load balancer?

If all traffic goes through one LB, **the LB is a single point of failure**. Solutions:

- **Active–passive pair:** two LBs share a floating "virtual IP"; if the active one stops sending heartbeats, the standby takes over the IP within seconds.
- **Managed cloud LBs** (AWS ALB/NLB, Google Cloud LB) are already distributed and redundant across zones. In interviews it's fine to say "a managed, highly available load balancer".
- **DNS / GeoDNS** in front spreads users across **regions**, each with its own LBs.

<Callout type="interview">
Draw the LB in almost every design between clients and app servers. Say: "an **L7 load balancer**, **least connections**, with **health checks**; it's managed and redundant across availability zones, and it terminates TLS." Then move on. Don't spend 10 minutes here unless asked.
</Callout>

<Takeaways>
- A load balancer spreads requests, **skips unhealthy servers** and lets you scale out invisibly.
- Algorithms: **round robin** (simple), **least connections** (uneven request times), **hash** (stickiness).
- **Health checks** detect dead servers; there's a short gap before detection.
- **L7** LBs understand HTTP and can route by path or header; **L4** LBs are faster but blind to content.
- Make the LB itself redundant: **active–passive pairs, managed cloud LBs, DNS across regions**.
</Takeaways>
