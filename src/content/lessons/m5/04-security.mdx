<Callout type="problem">
You've designed a fast, scalable, reliable system. Then an attacker floods it with 2 million requests per second, someone guesses that `/api/orders/1002` shows another user's order, a leaked API key in a public Git repo gives full database access, and a crafted search query dumps your users table. **Scale doesn't matter if the system isn't safe.**
</Callout>

Security is a huge field. For system design interviews, you need the **main layers** and the **classic mistakes**.

## Defense in depth

No single protection is perfect, so stack several layers. An attacker must get through **all** of them:

## The essentials checklist

**Encryption**
- **In transit:** HTTPS/TLS everywhere, including inside your network (mTLS) for sensitive systems.
- **At rest:** disk/database/backup encryption (managed keys via KMS). Hash passwords with **bcrypt/scrypt/Argon2** (slow, salted), never store them encrypted or plain.

**Authentication & authorization** (Module 4)
- Short-lived tokens, MFA for sensitive actions.
- Check **ownership on every request**. The #1 API vulnerability (OWASP API Top 10) is **BOLA/IDOR**: `/orders/1002` returning someone else's order because the server only checked "is logged in", not "is it yours". Random, non-sequential public IDs make guessing harder, but the **check** is the real fix.

**Input handling**
- **SQL injection:** always use parameterized queries / ORM bindings, never string concatenation.
- **XSS:** escape output, use a Content Security Policy (you know this from frontend!).
- **Validation:** allow-lists, size limits on uploads and request bodies, file type checks.

**DDoS and abuse**
- <Term k="ddos">DDoS</Term> protection at the edge (CDN, Cloudflare, AWS Shield), autoscaling, rate limiting, CAPTCHAs on sensitive forms, timeouts so slow attacks can't hold connections forever.

**Secrets**
- Never in code or Git. Use a **secrets manager** (AWS Secrets Manager, Vault), inject at runtime, **rotate** regularly.

**Least privilege & isolation**
- Every service, person and API key gets the **minimum permissions** needed.
- Network segmentation: public subnet only for load balancers; everything else private.

**Audit & monitoring**
- Log security events (logins, permission changes, admin actions) to tamper-resistant storage; alert on anomalies.

**Privacy & compliance**
- Collect less, encrypt PII, support deletion (GDPR "right to be forgotten"), keep data in required regions (data residency), PCI-DSS for card data (usually: let Stripe/Razorpay handle raw card numbers so they never touch your servers).

<Callout type="frontend">
Your frontend security knowledge counts here: **CSP**, **XSS** escaping, **CSRF** tokens / SameSite cookies, **CORS** configured narrowly, HttpOnly cookies for tokens, and **Subresource Integrity** for CDN scripts. Mention these when a design includes a web client.
</Callout>

<Callout type="interview">
You don't need a security deep-dive in most interviews, but a 30-second pass is a strong signal: "**TLS everywhere**, auth at the gateway, **authorization checks on resource ownership**, **rate limiting**, **WAF/DDoS** protection at the CDN, DB in a **private subnet** with **encryption at rest**, secrets in a **secrets manager**, and card data handled by the **payment provider** (PCI scope reduction)."
</Callout>

<Takeaways>
- **Defense in depth:** edge (CDN/WAF/DDoS) → gateway (authN, rate limits) → services (authZ, validation, mTLS) → data (private, encrypted, least privilege).
- Biggest real-world API bug: **missing ownership checks (BOLA/IDOR)**.
- **Parameterized queries**, output escaping, input limits.
- Secrets in a **manager**, never in code; **least privilege** everywhere; hash passwords with **bcrypt/Argon2**.
</Takeaways>
