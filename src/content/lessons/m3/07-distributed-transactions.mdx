<Callout type="problem">
Booking a trip needs three services: **Flights** (reserve a seat), **Hotels** (reserve a room) and **Payments** (charge the card). Each has its own database. If the hotel is full after we already reserved the flight and charged the card, we're in trouble. There's no `BEGIN ... COMMIT` that spans three databases owned by three teams. **How do we keep this all-or-nothing?**
</Callout>

## Option 1: Two-phase commit (2PC)

## Option 2: Sagas

A <Term k="saga">saga</Term> splits the big transaction into a **sequence of local transactions**, one per service. Each step has a **compensating action** that undoes it. If a step fails, run the compensations for the steps that already succeeded, in reverse.

| Step | Action | Compensation |
|---|---|---|
| 1 | Reserve flight seat | Release seat |
| 2 | Reserve hotel room | Release room |
| 3 | Charge card | Refund card |
| 4 | Confirm booking | (none, last step) |

If step 3 (payment) fails: refund isn't needed, so **release room → release seat**. The system ends up consistent, just not instantly: for a moment, a seat was reserved for a booking that didn't happen.

### Orchestration vs choreography

- **Orchestration:** a central orchestrator tells each service what to do (above). Easy to understand and monitor. Tools: Temporal, AWS Step Functions, Camunda.
- **Choreography:** no central brain; each service listens to events and reacts ("FlightReserved" → hotel service reserves → "HotelReserved" → payment charges…). Loosely coupled, but the overall flow is hard to see and debug.

### Saga gotchas

- Compensations must be **idempotent** and **retryable** (they may run more than once).
- Some actions **can't be undone** (an email was sent). Put them **last**, or design a "semantic" compensation (send a correction email).
- Users can see **intermediate states** (a seat "pending"). Use statuses like `PENDING → CONFIRMED / CANCELLED` and show them honestly.

## The outbox pattern: "update DB and publish event" safely

Sagas and event-driven systems constantly need to **update the database and publish an event**. Doing them separately is a "dual write": the app might crash between them, so the DB changed but no event was sent (or vice versa).

**Transactional outbox:** in the **same local transaction**, write the business change **and** an "outbox" row describing the event. A separate relay process (or CDC) reads the outbox table and publishes to Kafka, retrying until it succeeds.

```sql
BEGIN;
UPDATE orders SET status = 'PAID' WHERE id = 991;
INSERT INTO outbox (event_type, payload) VALUES ('OrderPaid', '{"orderId": 991}');
COMMIT;
-- relay: SELECT unsent rows from outbox → publish to Kafka → mark sent
```

Now the event is published **if and only if** the transaction committed (at least once, so consumers stay idempotent).

<Callout type="interview">
In microservice designs with multi-step business flows (bookings, orders, payments), say: "We can't use a single ACID transaction across services, so we use a **saga with compensating actions**, **orchestrated** by a workflow engine like Temporal. Each service publishes events via the **outbox pattern**, and all handlers are **idempotent**." Mention that **2PC** exists but blocks and doesn't fit microservices well.
</Callout>

<Takeaways>
- Normal transactions don't span services. Options: **2PC** or **sagas**.
- **2PC:** prepare + commit; truly atomic but **blocking and slow**; rare in microservices.
- **Saga:** sequence of local transactions + **compensations** on failure; **eventually consistent**.
- **Orchestration** (central coordinator) vs **choreography** (events). Orchestration is easier to reason about.
- Use the **outbox pattern** to update the DB and publish events reliably.
</Takeaways>
