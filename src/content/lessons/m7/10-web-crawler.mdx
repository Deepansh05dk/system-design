<Callout type="problem">
To build a search engine you must first **download the web**: billions of pages, refreshed regularly. Start from a few seed URLs, fetch each page, extract its links, add new links to the to-do list, repeat. That's BFS on a graph with billions of nodes, where the "graph" is hostile: servers are slow, some sites are infinite traps, many pages are duplicates, and hammering a small site with 1,000 requests a second is effectively attacking it.
</Callout>

## Step 1: Requirements

**Functional**
1. Given seed URLs, crawl pages, extract links, and keep discovering new pages.
2. Store page content for the indexer (search engine).
3. Re-crawl pages periodically (news sites often, static pages rarely).

**Non-functional**
- **Scale:** ~1 billion pages per month (and more over time).
- **Politeness:** respect `robots.txt`; don't overload any single host.
- **Robustness:** survive bad HTML, timeouts, crawler traps, huge files.
- **Efficiency:** don't download the same URL or the same content twice.
- **Extensible:** later add new content types (images, PDFs).

## Step 2: Estimation

- 1B pages/month ≈ **~400 pages/sec** (peak ~800).
- Average page ~100 KB (HTML) → 100 TB/month of raw content → compressed and stored in object storage; ~1.2 PB/year.
- Bandwidth: 400 × 100 KB ≈ 40 MB/s ≈ 320 Mbps.
- URLs seen: tens of billions over time → the "seen URL" set needs a **Bloom filter** or a large KV store.

## Deep dives

### The URL frontier: priority + politeness

Two layers of queues:
1. **Front queues (priority):** a prioritizer scores URLs (PageRank-like importance, how often the page changes, freshness needs) and puts them into high/medium/low queues.
2. **Back queues (politeness):** one queue **per host**. Each host queue is assigned to one fetcher thread, with a delay between requests (e.g. ≥ 1 s or the `Crawl-delay` from robots.txt). A min-heap of "next allowed fetch time per host" tells workers which host is ready.

This guarantees we never hit `smallblog.com` with 50 parallel requests, while still keeping all workers busy across millions of hosts.

### Deduplication

- **URL dedup:** normalize, then check a **Bloom filter** (fast, memory-efficient, false positive = we skip a page we haven't really seen: acceptable) backed by a distributed KV store for exact checks if needed.
- **Content dedup:** hash of the content for exact duplicates; **SimHash/MinHash** for near-duplicates (same article with different ads).

### Traps and a hostile web

- **Crawler traps:** infinite calendars (`/calendar?month=…` forever), session IDs in URLs, endlessly deep paths. Limit URL length and depth per host, cap pages per host, detect repeating patterns.
- **Timeouts and size limits** for slow or huge responses; only fetch content types you handle.
- **Spam and malware:** reputation scores, skip low-quality hosts.

### Freshness (re-crawling)

Track how often each page changes; re-crawl frequently changing pages (news homepages: minutes) far more often than stable ones (old blog posts: months). Use `ETag`/`Last-Modified` with conditional GETs to avoid re-downloading unchanged pages.

### Scaling out

Partition the frontier **by host** (hash of hostname → crawler node), so politeness for a host is enforced in one place, and DNS/robots caches are local. Crawl nodes can be placed in several regions to fetch sites closer to them.

Must mention: **BFS with a URL frontier**, **politeness via per-host queues + robots.txt**, **URL normalization + Bloom filter for "seen"**, **content dedup with hashing**, **trap protection**, **DNS caching**, and **partitioning by host**. Showing you understand the web is hostile (traps, slow servers, duplicates) is the senior-level signal.
</Callout>

<Takeaways>
- It's BFS over the web graph, driven by a **URL frontier** that handles **priority** and **politeness**.
- **Per-host queues + robots.txt + delays** keep the crawler polite.
- **Bloom filters** for seen URLs; **hashes/SimHash** for duplicate content.
- Defend against **traps, slow/huge responses**; re-crawl by **change frequency**; **partition by host**.
</Takeaways>
