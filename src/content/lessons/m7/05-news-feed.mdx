<Callout type="problem">
200 million people open Twitter (X) every day and expect their home timeline, the latest posts from everyone they follow, to load **instantly**. Some accounts have 100 million followers. When one of them posts, how do 100 million timelines get updated? And when you open the app, how is "the latest 50 posts from 400 people" assembled in under 200 ms?
</Callout>

## Step 1: Requirements

**Functional**
1. Post a tweet (text up to 280 chars, optional media).
2. Follow / unfollow users.
3. **Home timeline:** recent tweets from people you follow, newest first (ranking as a stretch).
4. User timeline: one user's own tweets.
*(Out of scope: search, trends, DMs, notifications. Mention them as separate systems.)*

**Non-functional**
- **Read-heavy:** timeline reads ≫ posts.
- Timeline loads in **< 200 ms** p99.
- **Highly available**; **eventual consistency** is fine: a new tweet can take a few seconds to show up in followers' timelines.
- Must handle **celebrity accounts** with tens of millions of followers.

## Step 2: Estimation

- 200M DAU, each posts ~2 tweets/day → 400M tweets/day ≈ **~5K writes/sec** (peak ~15K).
- Each user opens the timeline ~10×/day → 2B timeline reads/day ≈ **~23K reads/sec** (peak ~70K), each returning ~50 tweets.
- Average follows: ~200; some users have 100M followers.
- Tweet storage: 400M × ~300 B ≈ 120 GB/day (text + metadata; media separately in S3 + CDN).

**Conclusion:** reads dominate, and reads need data from **many** users. Assembling a timeline on the fly (query 200 users' tweets, merge, sort) at 70K/sec is expensive. → **Precompute timelines.**

## Step 3: API

```http
POST /v1/tweets                        { text, mediaIds? }       → 201 { tweetId }
POST /v1/users/{id}/follow             / DELETE to unfollow
GET  /v1/timeline/home?cursor=…&limit=50   → { tweets: [...], nextCursor }
GET  /v1/users/{id}/tweets?cursor=…
```

## Step 4: Data model

```sql
tweets  (tweet_id BIGINT PK  -- Snowflake: time-sortable
         user_id, text, media_urls, created_at)
         -- sharded by tweet_id (or user_id); index (user_id, tweet_id DESC) for user timelines
follows (follower_id, followee_id, created_at)
         -- PK (follower_id, followee_id) → "who do I follow"
         -- + reverse table/index (followee_id, follower_id) → "who follows me" (needed for fan-out)
users   (user_id PK, name, handle, follower_count, ...)

home_timeline cache (Redis):  timeline:{user_id} → list of the latest ~800 tweet_ids
```

**Snowflake IDs** for tweets mean sorting by ID = sorting by time, and pagination cursors are just tweet IDs.

**Hybrid (what Twitter actually did):** push tweets from normal users into followers' cached timelines; for accounts above a follower threshold, **don't push**. When you open your timeline, fetch your precomputed list **plus** recent tweets from the few celebrities you follow, and merge.

## Deep dives

**The celebrity threshold.** If a user follows 5 celebrities, the read path does 1 list read + 5 small "latest tweets of user X" reads (each cached). Cheap. Pushing a 50M-follower tweet would be 50M Redis writes: minutes of delay and huge load. That's why the hybrid wins.

**Inactive users.** Don't maintain cached timelines for people who haven't logged in for 30 days. When they return, **rebuild** their timeline on the fly (pull mode) and start pushing again.

**Timeline storage size.** Store only **IDs** (8 bytes) in timelines, not full tweets: 800 IDs × 8 B × ~100M active users ≈ **640 GB** of Redis. Large but feasible across a cluster (Twitter kept similar timeline caches in Redis).

**Deletes and unfollows.** Deleting a tweet: mark it deleted in the tweet store; hydration filters it out (don't chase it across millions of lists). Unfollow: filter at read time and/or clean the list lazily.

**Ranking (stretch).** Instead of pure time order, fetch a few hundred candidate tweets (from the cached timeline + celebrities + "you might like"), score them with an ML model (engagement predictions), and return the top 50. Candidate generation → ranking → filtering is the standard recommendation pipeline.

**Counts (likes/retweets).** Hot counters → Redis with sharded counters for viral tweets, persisted asynchronously (Module 3: hot keys).

<Callout type="frontend">
Client-side tricks matter too: **cursor-based infinite scroll**, showing a "**12 new posts**" pill instead of auto-inserting tweets (so the list doesn't jump), optimistic posting, and prefetching the next page. These are great to mention, especially in a frontend system design round (Module 8).
</Callout>

<Callout type="interview">
The heart of this question is **fan-out on write vs read**, and the **celebrity problem**. State both options with their costs, propose the **hybrid**, and back it with numbers. Then cover: Redis timelines of **IDs**, **Kafka-driven async fan-out**, **Snowflake IDs** for ordering and cursors, and **eventual consistency** being acceptable.
</Callout>

<Takeaways>
- Read-heavy + multi-user reads → **precompute timelines** (fan-out on write) into Redis lists of **tweet IDs**.
- **Celebrities** break push → **hybrid**: push for normal users, pull celebrities at read time.
- Post path: **store tweet → Kafka → fan-out workers**; read path: **ID list + merge + hydrate**.
- Skip inactive users, filter deletes at read time, rank as a separate pipeline.
</Takeaways>
