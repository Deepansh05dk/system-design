<Callout type="problem">
Two billion users. 100 billion messages a day. A message sent from Mumbai should appear on a phone in Toronto in well under a second, with ✓ (sent), ✓✓ (delivered) and blue ✓✓ (read). If the receiver's phone is off for three days, the message must still arrive, exactly once, in order. And the sender's phone is on a train going through tunnels.
</Callout>

## Step 1: Requirements

**Functional**
1. 1:1 messaging (text; media as a stretch).
2. Group chats (up to ~500 members).
3. Delivery status: sent, delivered, read.
4. Offline users receive messages when they come back (plus a push notification).
5. Online / last-seen presence.
6. Message history synced across a user's devices *(stretch)*.

**Non-functional**
- **Low latency:** < 500 ms delivery when both are online.
- **Reliable:** no message lost; no duplicates shown; per-conversation **order preserved**.
- **Highly available**; huge scale (hundreds of millions of concurrent connections).
- Security: end-to-end encryption *(mention; the server just relays ciphertext)*.

## Step 2: Estimation

- 500M DAU, ~40 messages/user/day → 20B messages/day ≈ **230K messages/sec** (peak ~700K).
- Message ~100 bytes + metadata → ~3 TB/day stored (if kept on server).
- Concurrent connections: ~100M+. At ~100K–500K connections per gateway server → **hundreds of connection servers**.

**Conclusion:** the hard parts are **holding millions of persistent connections**, **routing** messages to whichever server holds the receiver's connection, and **reliable delivery** with ordering, all at very high write volume.

## Step 3: Connection protocol

Clients keep a **persistent WebSocket** (WhatsApp historically used a custom XMPP-like protocol over TCP) to a **chat gateway** server. Server can push instantly; the client sends messages up the same connection. Heartbeats every ~30 s detect dead connections. (Review: Module 4, Real-Time.)

## Step 4: Data model

```text
messages (Cassandra / ScyllaDB / HBase)
  partition key: conversation_id
  clustering key: message_id (time-ordered, e.g. Snowflake / per-conversation sequence)
  columns: sender_id, body (encrypted), type, created_at

conversations (conversation_id, type: direct|group, members, created_at)
user_inbox / sync state: (user_id, conversation_id, last_delivered_id, last_read_id)
sessions (Redis): user_id → { gateway server, device } with TTL refreshed by heartbeats
```

Why a wide-column store: **massive write volume**, and messages are read "by conversation, newest first" (Module 1: NoSQL types). Discord did exactly this with Cassandra, then ScyllaDB.

## Deep dives

**Ordering.** Global ordering across all chats is impossible and unnecessary. What matters is **per-conversation order**. Give each message a monotonically increasing ID **within its conversation** (assigned by the service owning that conversation's partition), and have clients sort by it. Clients may receive messages out of order over the network and reorder before display.

**Exactly-once (as the user sees it).** The network gives at-least-once. Make it look exactly-once with **client message IDs** (server dedup) + **server message IDs** (client dedup).

**Presence (online / last seen).** Updated by heartbeats into Redis with TTL. Don't broadcast every change to every contact (huge fan-out): send presence only to users who currently have your chat open, or fetch on demand.

**Multi-device sync.** Each device tracks its own `last_synced_id` per conversation and pulls missing messages on connect. The server is the source of truth.

**Media.** Photos/videos are uploaded to object storage (pre-signed URL, encrypted on the client); the message only carries a pointer + decryption key.

**Storage policy.** WhatsApp historically deleted messages from servers once delivered (the phone held history). Many others (Slack, Discord, Messenger) keep history forever. State your choice; it changes storage needs dramatically.

**End-to-end encryption.** With the Signal protocol, clients encrypt with the receiver's keys; servers only see ciphertext and metadata. The server design stays the same, but servers can't search or moderate content.

<Callout type="interview">
Must-cover points: **persistent WebSocket connections** to gateway servers, a **session store** mapping user → gateway, **persist before deliver**, **ACKs and receipts** (✓ ✓✓), **dedup with client message IDs**, **per-conversation ordering**, **offline sync + push notifications**, and **Cassandra partitioned by conversation**. For groups, discuss fan-out size.
</Callout>

<Takeaways>
- Persistent **WebSocket** connections to stateless-ish **gateways**; **session store** maps users to gateways.
- **Persist first** (wide-column store partitioned by conversation), then route and push.
- **ACK flow**: sent ✓ after persist, delivered ✓✓ after receiver ACK, read on open.
- **Client IDs** for dedup; **per-conversation sequence** for ordering.
- Offline: **store + push notification + sync from last seen ID**.
</Takeaways>
