<Callout type="problem">
An e-commerce site processes 1 million orders a day. Every one must charge the customer **exactly once**, record the money correctly, pay the seller, survive network timeouts with the card network, and pass an audit. A bug here doesn't show a wrong like count; it **loses real money** or charges someone twice. In payment systems, **correctness beats everything**.
</Callout>

## Step 1: Requirements

**Functional**
1. Accept payments for orders (cards, UPI, wallets) via external **payment service providers (PSPs)** like Stripe, Razorpay, Adyen.
2. Track each payment's status; notify the order system.
3. Refunds.
4. Record every money movement in a **ledger**; pay out sellers *(stretch)*.
5. Reconcile with PSP/bank reports daily.

**Non-functional**
- **Correctness:** no double charges, no lost payments, every rupee accounted for.
- **Reliability:** retries must be safe; recover from any crash mid-flow.
- **Auditability:** immutable history.
- **Security & compliance:** PCI DSS: never store raw card numbers yourself.
- Throughput is modest (1M/day ≈ 12/sec; peaks ~1,000/sec on sale days). Latency matters less than correctness.

## Step 2: Don't touch card numbers

Use the PSP's hosted checkout/SDK: the card details go **directly from the browser/app to the PSP**, which returns a **token**. Your servers only see the token. This keeps you out of most PCI scope, which is a huge cost and risk reduction.

## Step 4: Payment state machine

```text
CREATED → PENDING → SUCCEEDED → (REFUND_PENDING → REFUNDED)
                  ↘ FAILED
                  ↘ UNKNOWN → (resolved by status query / webhook / reconciliation)
```

Every transition is validated (`UPDATE ... WHERE status = 'PENDING'`) and recorded. Never jump states arbitrarily; never "delete" a payment.

## Step 5: The ledger: double-entry bookkeeping

Accountants solved "keep money correct" 500 years ago: every transaction has **two sides that sum to zero**. Money never appears or disappears; it moves between accounts.

| entry_id | txn_id | account | debit | credit |
|---|---|---|---|---|
| 1 | pay_991 | customer_funds (asha) | ₹2,000 | |
| 2 | pay_991 | merchant_payable (shop_7) | | ₹1,940 |
| 3 | pay_991 | platform_fee_revenue | | ₹60 |

- Ledger rows are **append-only** (immutable). Corrections are **new** reversing entries, never edits.
- **Invariant:** for every transaction, total debits = total credits. Run continuous checks; any imbalance is an alert.
- Balances are **derived** by summing entries (with periodic snapshots for speed). This is event sourcing (Module 4).

## Deep dives

**Exactly-once effects.** Networks give at-least-once. You get exactly-once **effects** by combining: idempotency keys (client → us, us → PSP), unique constraints, conditional state transitions, deduplicated webhooks, and idempotent event consumers.

**Database choice.** Strong consistency and transactions: **PostgreSQL/MySQL** (with synchronous replica for zero data loss on failover), or distributed SQL at very large scale. Not an eventually consistent store.

**Multi-step flows (order → payment → inventory).** Use a **saga** (Module 3): if inventory reservation fails after payment, the compensating action is a **refund**.

**Retries and timeouts.** Retry PSP calls with backoff using the same idempotency key. Use circuit breakers and maybe a second PSP for failover (routing by success rate and cost).

**Security.** Tokenization (no raw cards), encryption, strict access controls, audit logs, fraud checks (velocity rules, ML risk scores) before charging.

<Callout type="interview">
Say these words: **idempotency keys end to end**, **payment state machine with conditional transitions**, **PSP tokenization (stay out of PCI scope)**, **signed + deduplicated webhooks**, **double-entry append-only ledger**, **outbox for events**, **daily reconciliation**. Make it clear you prioritize **correctness over latency** in this domain.
</Callout>

<Takeaways>
- Never handle raw cards: **PSP tokens**.
- **Idempotency keys** everywhere + unique constraints → no double charges on retries.
- An explicit **state machine**; handle the **unknown outcome** by retrying safely or querying status.
- **Double-entry, append-only ledger**: debits = credits, corrections are new entries.
- **Outbox** for reliable events, **webhooks** deduplicated, **reconciliation** to catch everything else.
</Takeaways>
