<Callout type="problem">
Users paste text (code, logs, notes), up to a few MB, and get a link like `paste.io/k8Fz2Qa` to share. Pastes can be public or unlisted, and can expire after 10 minutes, a day, or never. It looks like the URL shortener, but now the **content is big**, which changes where it's stored.
</Callout>

## Step 1: Requirements

**Functional**
1. Create a paste (text, optional title, syntax language, expiry, visibility) → get a unique link.
2. View a paste by link (raw and syntax-highlighted).
3. Pastes expire automatically.
4. *(Stretch)* Users can list/delete their pastes.

**Non-functional**
- Read-heavy (assume 10:1), low-latency reads, durable until expiry, highly available.
- Max paste size: 10 MB.

## Step 2: Estimation

- 1M new pastes/day → ~12 writes/sec; 10M reads/day → ~120 reads/sec (peak ~500).
- Average paste ~10 KB → 10 GB/day → **~3.6 TB/year** of content.
- Metadata ~200 bytes/paste → 73 GB/year. Small.

**Conclusion:** traffic is modest; the interesting part is **storing lots of text content** cheaply and serving it fast.

## Step 3: API

```http
POST /api/v1/pastes
  body: { "content": "...", "title"?: "...", "language"?: "python", "expiresIn"?: "1d", "visibility": "unlisted" }
  → 201 { "key": "k8Fz2Qa", "url": "https://paste.io/k8Fz2Qa" }

GET /api/v1/pastes/{key}        → 200 { metadata + content }  (404 / 410 Gone if expired)
GET /raw/{key}                  → text/plain content
DELETE /api/v1/pastes/{key}     (owner only)
```

```sql
pastes (
  key          VARCHAR(10) PRIMARY KEY,
  user_id      BIGINT NULL,
  title        TEXT,
  language     VARCHAR(30),
  visibility   VARCHAR(10),   -- public | unlisted | private
  size_bytes   INT,
  s3_key       TEXT,          -- e.g. pastes/k8/k8Fz2Qa
  created_at   TIMESTAMP,
  expires_at   TIMESTAMP NULL
)
-- index: (user_id, created_at) for "my pastes"; (expires_at) for cleanup
```

Keys are generated like the URL shortener (ID range + base62, or random 7–8 chars with a uniqueness check). For **unlisted** pastes, keys must be **random enough** that nobody can guess them.

## Deep dives

**Why check expiry at read time if a job deletes them anyway?** The cleanup job runs every few minutes; a "burn after 10 minutes" paste must stop being readable exactly on time. Lazy check on read = correctness; background job = storage reclamation.

**Deduplication (optional):** many users paste the same stack trace. Store content by **content hash** (`sha256(content)`) so identical pastes share one object. Saves storage; needs reference counting before deleting.

**Rendering:** syntax highlighting can happen **client-side** (Shiki/Prism in the browser) so servers just return raw text. That's simpler and cheaper for the backend.

<Callout type="frontend">
You'd likely build the viewer: lazy-load the highlighter, virtualize very long pastes (100K lines) so the DOM doesn't explode, and offer "raw" links for huge pastes.
</Callout>

<Callout type="interview">
The key insight interviewers look for: **separate metadata (DB) from content (object storage)**, serve public content through a **CDN**, and handle **expiry** both lazily on read and with a background cleanup job. The rest is shared with the URL shortener, so say "key generation works like a URL shortener" and move on.
</Callout>

<Takeaways>
- **Metadata in the DB, content in S3**; the DB stays small and fast.
- Unlisted pastes need **unguessable random keys**.
- Expiry: **check on read** (exact) + **background cleanup** (storage).
- Cache hot pastes in Redis; serve public raw content via **CDN**; highlight on the client.
</Takeaways>
