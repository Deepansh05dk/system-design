<Callout type="problem">
Your platform must run: "send this reminder at 9:00 AM tomorrow", "generate every merchant's invoice on the 1st of each month", "retry this failed webhook in 5 minutes", "clean expired sessions every hour". That's millions of jobs, each must run **on time**, **once**, and **survive any server crashing**. A single server with crontab won't cut it.
</Callout>

## Step 1: Requirements

**Functional**
1. Submit a job: one-off at a time (`runAt`) or recurring (`cron` expression), with a payload / target (HTTP endpoint, queue, function).
2. Execute jobs at (or very close to) their scheduled time.
3. Retries with backoff on failure; max attempts; dead-letter.
4. Query job status/history; cancel/pause jobs.

**Non-functional**
- **Reliable:** no scheduled job silently lost; crashes don't drop jobs.
- **At-least-once execution**, avoiding duplicates as much as possible (jobs should be idempotent).
- **Timeliness:** start within ~1–5 seconds of the scheduled time.
- **Scalable:** 10M+ jobs/day, with spikes (e.g. many jobs at midnight).
- Highly available scheduler (no single point of failure).

## Step 2: Estimation

- 10M jobs/day ≈ 115/sec average; but **bursty**: "midnight" or "every hour on the hour" can mean 1M jobs at the same second.
- Job record ~1 KB → 10 GB/day of history (keep 30 days ≈ 300 GB).

## Step 3: Data model

```sql
jobs (
  job_id        UUID PK,
  owner, type,  -- http | queue | function
  payload       JSONB,
  schedule      TEXT NULL,       -- cron expression for recurring jobs
  next_run_at   TIMESTAMP,       -- when it should run next
  status        TEXT,            -- SCHEDULED | RUNNING | SUCCEEDED | FAILED | PAUSED
  attempts      INT, max_attempts INT,
  lease_owner   TEXT NULL, lease_until TIMESTAMP NULL,
  version       INT
)
-- index (status, next_run_at)  ← "what is due now?"
job_runs (run_id, job_id, started_at, finished_at, result, error)
```

The critical query: **"give me jobs with `next_run_at <= now` that nobody is running"**, fast, without two schedulers grabbing the same job.

## Deep dives

**Leases and crashes.** A worker or scheduler may die after claiming a job. The **lease** (`lease_until`) handles it: a recovery sweep re-schedules jobs whose lease expired while still RUNNING. This is why execution is **at-least-once**: a job may run twice if a worker finished but died before recording success. Therefore jobs must be **idempotent** (or carry an idempotency key to the target).

**Avoiding duplicate claims.** Atomic claim via conditional UPDATE / `SKIP LOCKED`, plus partition ownership so normally only one scheduler even looks at a job. Fencing tokens (lease version) prevent a "zombie" worker from overwriting a newer run's result.

**Hot moments (midnight spikes).** 1M jobs due at 00:00:00:
- Claim in **batches**, many partitions in parallel.
- **Pre-load** upcoming jobs: every minute, fetch jobs due in the next minute into an in-memory **timing wheel / delay queue** per scheduler, so execution is precise and the DB isn't hit at the exact second.
- Encourage clients to add **jitter** ("around midnight") when exact time doesn't matter.

**Storage partitioned by time.** Using time buckets (e.g. one partition per minute) makes "what's due now?" a scan of a small bucket, and old buckets can be archived cheaply. Many large systems store far-future jobs in a cheap store and move them into a "hot" short-term queue (like Redis sorted sets keyed by timestamp, or SQS delay queues) as their time approaches.

**Recurring jobs.** Store the cron expression; after each run compute the next time. Decide policy for **missed runs** after an outage: run once now (catch-up) or skip to the next slot.

**Simpler alternatives.** For moderate scale, a Postgres table with `FOR UPDATE SKIP LOCKED` + a worker pool, or managed tools (AWS EventBridge Scheduler, Temporal, Quartz cluster, Sidekiq/Celery beat), may be enough. Saying so shows judgment.

<Callout type="interview">
Cover: **durable job store with an index on next_run_at**, **partitioned schedulers with ownership via etcd/ZooKeeper** (no SPOF), **atomic claiming (conditional update / SKIP LOCKED) with leases**, **queue + separate workers**, **retries with backoff + DLQ**, **at-least-once → idempotent jobs**, and **handling bursts** (pre-loading, timing wheels, jitter).
</Callout>

<Takeaways>
- Store jobs durably with **next_run_at**; scan only **due** jobs via an index or time buckets.
- **Partition** the work; assign partitions with **consensus** so scheduler nodes can fail over.
- **Claim atomically with leases**; expired leases are re-run → **at-least-once**, so jobs must be **idempotent**.
- Separate **scheduling** from **execution** with a queue; retries with backoff; DLQ.
- Smooth **bursts** with pre-loading, in-memory timing wheels and jitter.
</Takeaways>
