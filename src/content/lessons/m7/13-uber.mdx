<Callout type="problem">
Millions of drivers send their GPS location **every 4 seconds**. When a rider taps "Book", the system must find the best nearby available driver within a second or two, make sure two riders never get the same driver, track the trip live on both phones, and compute the fare. Location data changes constantly, which is the opposite of most databases' comfort zone.
</Callout>

## Step 1: Requirements

**Functional**
1. Drivers go online/offline and continuously report location.
2. Riders see nearby cars on the map and get an ETA/price estimate.
3. Rider requests a ride → system **matches** a nearby driver → driver accepts/declines.
4. Live trip tracking for both sides; trip completion and fare.
*(Out of scope: payments details, ratings, surge-pricing algorithm, scheduled rides. Mention them.)*

**Non-functional**
- **Low latency matching** (seconds) and live updates (~1–4 s freshness).
- **Consistency for assignments:** a driver must never be assigned to two riders.
- **Highly available** (people stranded otherwise).
- Scale: e.g. 5M active drivers at peak, 20M rides/day.

## Step 2: Estimation

- Location updates: 5M drivers ÷ 4 s ≈ **1.25M writes/sec**. Each update is tiny (~100 bytes) → ~125 MB/s.
- Ride requests: 20M/day ≈ ~230/sec average (peaks of several thousand/sec in busy cities).

**Conclusion:** location updates are **extremely write-heavy** and **only the latest value matters**. They must live **in memory**, not as rows in a disk-based database. Trip records, by contrast, are lower volume and need durability and consistency.

## Step 3: Geospatial indexing (recap)

To find "available drivers within 2 km" quickly, index drivers by **cell** (geohash, Google S2 or Uber's own **H3 hexagons**). Look up the rider's cell and its neighbours, then rank candidates by real ETA.

## Deep dives

**Why in memory?** 1.25M updates/sec where only the latest matters: a disk-based B-tree database would spend all its time rewriting index pages. In-memory structures (sharded by region) handle this easily; losing them in a crash is fine because drivers re-report within seconds.

**Sharding by geography.** Most queries are local, so partition location and matching **by city/region**. A busy city (e.g. Mumbai) may need several shards (by H3 cells). Cross-border queries look at neighbouring shards.

**No double assignment.** Two matching requests could pick the same driver at the same moment. Protect with an atomic state transition on the driver/trip record: `UPDATE drivers SET status='assigned', trip_id=? WHERE id=? AND status='available'`. The loser retries with the next candidate. (Module 3: concurrency.)

**Trip state machine.** `requested → driver_assigned → driver_arrived → in_progress → completed / cancelled`. Transitions are validated and stored durably; every transition is an event (for notifications, billing, analytics). The trip DB needs **strong consistency** and durability; this is where a relational DB or a strongly consistent distributed DB fits.

**Live tracking.** During a trip, the driver's location updates are forwarded to the rider's connection (pub/sub keyed by trip ID). Clients interpolate between points for smooth movement.

**Surge pricing (mention).** A stream job compares demand (requests) vs supply (available drivers) per cell every minute; multipliers are published to the pricing service.

**Reliability.** If a region's matching service fails, riders must still be able to complete trips. Uber famously used phone-side state as a backup so active trips could recover after a data center failover.

<Callout type="interview">
Key points: **location updates are extremely write-heavy and ephemeral → in-memory geo index (geohash/S2/H3), sharded by city**, **history via Kafka to cheap storage**, **matching by ETA over nearby cells**, **atomic driver assignment** (no double booking), and a **durable trip state machine**. Show the numbers that justify in-memory storage.
</Callout>

<Takeaways>
- ~1M+ location writes/sec, only the latest matters → **in-memory geo index**, **sharded by geography**.
- Find drivers via **cells + neighbours**, rank by **road ETA**.
- **Atomic conditional updates** prevent assigning one driver twice.
- **Trip state machine** in a strongly consistent store; location history and analytics via **Kafka → S3/warehouse**.
</Takeaways>
