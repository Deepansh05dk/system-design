<Callout type="problem">
You run a public API used by 50,000 developers. You need to enforce limits like "100 requests per minute per API key on the free plan, 10,000 on pro", "5 login attempts per minute per IP", and a global safety limit, across **200 API servers**, adding no more than a millisecond of latency.
</Callout>

Review the algorithms first if needed: **Module 3: Rate Limiting**. Here we design the **whole system**.

## Step 1: Requirements

**Functional**
1. Limit requests per **key** (API key, user ID, IP) per **rule** (endpoint + window).
2. Rules are configurable per plan/endpoint without redeploying.
3. Rejected requests get **429** with `Retry-After` and remaining-quota headers.
4. Limits are **global** across all API servers.

**Non-functional**
- **Low latency:** < 1–2 ms added per request.
- **Highly available:** if the limiter breaks, the API should keep working (usually **fail open**).
- **Accurate enough:** small over-limit tolerance (a few %) is OK; huge overshoot is not.
- Scale: 1M requests/sec overall, 10M+ distinct keys.

## Step 2: Choose the algorithm

<RateLimiterSim />

For an API platform: **token bucket** (allows short bursts, simple, 2 numbers per key) or **sliding window counter** (smooth and accurate). Both store tiny state per key, which matters with 10M keys.

Memory estimate: 10M keys × ~50 bytes ≈ **500 MB** of Redis. Easily fits; shard across a few Redis nodes for throughput (1M ops/sec).

The token bucket in Redis (pseudo-code for the Lua script):

```lua
-- KEYS[1] = bucket key, ARGV = capacity, refill_per_sec, now_ms
local capacity = tonumber(ARGV[1])
local refill_per_sec = tonumber(ARGV[2])
local now = tonumber(ARGV[3])  -- or derive it from redis.call('TIME') to avoid gateway clock skew
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or capacity
local ts = tonumber(b[2]) or now
tokens = math.min(capacity, tokens + (now - ts) / 1000 * refill_per_sec)
local allowed = tokens >= 1
if allowed then tokens = tokens - 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], 120000)   -- idle keys disappear
return { allowed and 1 or 0, math.floor(tokens) }
```

## Deep dives

<Callout type="why" title="Why not a counter in each gateway's memory?">
200 gateways each allowing 100/min = up to **20,000/min** for one key. Local counters are only OK as an **approximation** layer: e.g. each gateway gets limit/N, or local buckets sync to Redis every few hundred ms. That saves the Redis call at the cost of accuracy. Mention it as an optimization for extreme scale.
</Callout>

**Race conditions:** two gateways read "99 used", both allow, both write 100 → 101 requests passed. Fix: **atomic** operations (Lua script, or `INCR` which is atomic, for fixed windows).

**Fail open vs fail closed:** if Redis is unreachable:
- **Fail open** (allow): the API stays up; you temporarily lose limits. Usual choice for general APIs.
- **Fail closed** (reject): safer for abuse-sensitive endpoints (login, OTP, payments).
- Also: tight timeout (a few ms) on the Redis call so a slow Redis doesn't slow the API.

**Multi-region:** per-region Redis with limits split per region (simple, slightly inaccurate), or async replication of counters (complex). Usually: **per-region limits**.

**Clock issues:** use Redis server time (`TIME`) inside the script rather than each gateway's clock.

**Layered limits:** CDN/WAF (crude IP floods) → gateway (per key/plan) → service (protect a fragile DB, e.g. "max 50 concurrent report generations").

<Callout type="interview">
Hit these points: **token bucket or sliding window counter** (with why), **runs at the gateway**, **counters in Redis updated atomically (Lua)**, **rules cached in memory**, **429 + Retry-After**, **fail-open decision**, and **local approximation** as an optimization. That's a complete senior-level answer.
</Callout>

<Takeaways>
- Put the limiter **at the gateway**; keep rules **in memory**.
- Store per-key state in **Redis**; update it **atomically** (Lua/INCR) to avoid races.
- Return **429 + Retry-After + remaining headers**.
- Decide **fail open vs closed**, set tight timeouts, and consider **local approximations** at extreme scale.
</Takeaways>
