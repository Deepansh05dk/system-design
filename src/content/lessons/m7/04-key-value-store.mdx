<Callout type="problem">
Design a key-value store with two operations, `put(key, value)` and `get(key)`, that holds **hundreds of terabytes**, handles **millions of operations per second**, and **keeps working when servers die**. This question tests whether you can combine almost everything from Modules 2 and 3 into one coherent system. It's based on Amazon's famous **Dynamo** paper, which inspired DynamoDB, Cassandra and Riak.
</Callout>

## Step 1: Requirements

**Functional**
- `put(key, value)`, `get(key)`. Values up to ~1 MB. Optional `delete(key)`.

**Non-functional**
- **Huge scale:** horizontal scaling by adding nodes.
- **High availability:** always writable, even during failures (shopping cart style), so we lean **AP**.
- **Tunable consistency:** callers can choose stronger consistency for some operations.
- **Low latency:** single-digit ms at p99.
- **Durability:** data must survive node failures.

## Step 2: The core building blocks

| Problem | Technique | Module |
|---|---|---|
| Data too big for one machine | **Partitioning** with **consistent hashing** + virtual nodes | 2 |
| Machines fail | **Replication** to N nodes | 2 |
| Consistency vs availability | **Quorums**: R + W > N, tunable | 3 |
| Concurrent writes conflict | **Versioning**: vector clocks or last-write-wins | 3 |
| Temporary failures | **Sloppy quorum + hinted handoff** | below |
| Permanent failures / drift | **Anti-entropy with Merkle trees**, read repair | below |
| Who's alive? | **Gossip protocol** | below |
| Fast writes on disk | **Commit log + memtable + SSTables (LSM tree)** | 1 |

## Step 3: Partitioning and replication

Keys and nodes live on a **consistent hash ring**. A key is stored on the first node clockwise (its **coordinator**) **and the next N−1 distinct nodes** (N = 3 typically). Virtual nodes keep the load even and spread recovery work.

<HashRing />

## Step 4: Reads and writes with quorums

Any node can receive a client request and act as **coordinator** for that key. It forwards the write to all N replicas and waits for **W** acknowledgements; a read asks replicas and waits for **R** responses, returning the newest version.

<QuorumSim />

Typical settings with N = 3:
- **W = 2, R = 2:** balanced, read-your-writes via overlap, tolerates 1 node down.
- **W = 1, R = 1:** fastest and most available; eventual consistency.
- **W = 3, R = 1:** fast strongly-consistent reads, but writes fail if any replica is down.

## Deep dives

### Conflicts: two clients write the same key concurrently

- **Last-write-wins (LWW):** attach a timestamp; highest wins. Simple (Cassandra does this), but concurrent writes silently **lose data**, and clock skew can pick the "wrong" winner.
- **Vector clocks:** each version carries `{nodeA: 3, nodeB: 1}` counters. If neither version descends from the other, they're **siblings (a conflict)**; return both and let the application merge (Dynamo's shopping cart merged items from both versions).
- **CRDTs:** data types that merge automatically (counters, sets).

### Failure detection: gossip

Instead of a central monitor (a SPOF), each node periodically tells a few random nodes "here's my heartbeat and what I know about others". Information spreads like a rumor in O(log N) rounds. A node not heard from in a while is suspected down.

### Storage engine on each node (write path)

1. Append to a **commit log** on disk (durability).
2. Insert into an in-memory sorted **memtable**.
3. When full, flush it to disk as an immutable sorted **SSTable**.
4. Reads check the memtable, then SSTables (newest first), using **Bloom filters** to skip SSTables that can't contain the key.
5. **Compaction** merges SSTables in the background and drops overwritten/deleted values (deletes are written as **tombstones**).

That's an **LSM tree**: sequential writes, very high write throughput.

<Callout type="why" title="Why AP and not CP here?">
The Dynamo paper's motivation: "add to cart" must **never** fail, even during network problems. A briefly inconsistent cart (merged later) is better than a lost sale. If you're asked for a **strongly consistent** KV store instead (like etcd for config), you'd use a **leader per partition with Raft**, and writes would fail without a majority. Be ready to explain both.
</Callout>

<Takeaways>
- Partition with **consistent hashing + virtual nodes**; replicate to the next **N** nodes on the ring.
- Tune consistency with **quorums (R + W > N)**.
- Handle conflicts with **LWW** (simple, lossy) or **vector clocks/CRDTs** (merge).
- Availability under failure: **sloppy quorum + hinted handoff**; repair with **read repair + Merkle trees**; detect failures with **gossip**.
- Each node stores data in an **LSM tree** (commit log, memtable, SSTables, compaction, Bloom filters).
</Takeaways>
