<Callout type="problem">
100 million photos are uploaded to Instagram every day, and billions are viewed. Each photo must be resized into several versions for different screens, delivered fast anywhere in the world, and appear in followers' feeds. How do you build the photo pipeline so that uploads feel instant and viewing is fast on a slow phone connection?
</Callout>

## Step 1: Requirements

**Functional**
1. Upload a photo with a caption.
2. Follow users; see a **feed** of photos from people you follow.
3. Like and comment on photos.
4. View a user's profile grid.
*(Out of scope: stories, reels, DMs, search, explore. Mention they'd be separate services.)*

**Non-functional**
- Uploads must be **reliable** (never lose a photo) and feel fast.
- Feed and images load **quickly** worldwide (< 200 ms for feed data; images via CDN).
- **Read-heavy:** ~100 views per upload.
- Highly available; eventual consistency for feeds/likes is fine.

## Step 2: Estimation

- 500M DAU; 100M uploads/day → **~1,200 uploads/sec** (peak ~3K).
- Average original photo 2 MB, plus 4 resized versions (~500 KB total) → ~2.5 MB per photo → **250 TB/day** → ~90 PB/year (before replication). This is **object storage + CDN** territory.
- Views: 100M × 100 = 10B image views/day ≈ **115K image requests/sec**, almost all served by the **CDN**.
- Metadata per photo ~1 KB → 100 GB/day. Easily handled by a sharded DB.

## Step 3: API

```http
POST /v1/uploads             { contentType, size }  → { uploadUrl (pre-signed), photoId }
PUT  <uploadUrl>             (client → object storage directly)
POST /v1/posts               { photoId, caption }   → 201 { postId }
GET  /v1/feed?cursor=…       → { posts: [{ id, user, caption, imageUrls{thumb,medium,full}, likeCount, ... }], nextCursor }
POST /v1/posts/{id}/likes    / DELETE to unlike
POST /v1/posts/{id}/comments { text }
GET  /v1/users/{id}/posts?cursor=…
```

## Step 4: Data model

```sql
users     (user_id PK, username, bio, avatar_url, follower_count, ...)
posts     (post_id PK (Snowflake), user_id, caption, status, image_keys, created_at)
          -- index (user_id, post_id DESC) → profile grid
follows   (follower_id, followee_id)  + reverse index
likes     (post_id, user_id, created_at)   PK (post_id, user_id) → no double likes
comments  (comment_id PK, post_id, user_id, text, created_at)  -- index (post_id, comment_id)
```

- **Posts / users / follows:** sharded relational DB (Instagram famously ran on **sharded PostgreSQL**) or Cassandra.
- **Likes and comments:** huge volume, simple access ("by post, newest first") → Cassandra-style wide-column works well; keep `like_count` as a denormalized counter.
- **Images:** object storage; DB stores only keys.

## Deep dives

**Why process images asynchronously?** Resizing takes hundreds of ms of CPU; doing it in the request makes uploads slow and fragile. With a queue, workers scale independently, retries are automatic, and a spike of uploads just queues up. The app can show the local image immediately (**optimistic UI**) while processing finishes.

**Multiple sizes and formats.** A phone showing a 300 px grid tile shouldn't download a 4000 px original. Generate a few fixed sizes (or resize on the fly at the CDN edge with an image service) and let the client choose via `srcset`.

**Feed generation.** Same as the Twitter design: **hybrid fan-out** (push for normal accounts, pull for celebrities), Redis lists of post IDs, cursor pagination. Ranked feed = candidate generation + ML ranking.

**Likes at scale.** A viral post gets thousands of likes per second. Write individual likes to Cassandra (for "did I like this?" and lists), and increment a **sharded counter** in Redis for display, flushing to the DB periodically. The count can be eventually consistent.

**Storage cost.** 90 PB/year is expensive. Use **lifecycle tiers**: old, rarely viewed originals move to infrequent-access storage; keep the commonly served sizes hot.

**Privacy.** Strip EXIF GPS data, use unguessable image URLs (or signed URLs for private accounts), and check permissions in the post service, not the CDN.

<Callout type="frontend">
Frontend wins here are huge: responsive images with `srcset`/`sizes`, lazy loading below the fold, blur-up placeholders (store a tiny "blurhash" string with each post's metadata), and optimistic upload previews.
</Callout>

<Callout type="interview">
Key points: **pre-signed direct uploads**, **async processing pipeline** (queue + workers → multiple sizes), **metadata in a sharded DB vs bytes in object storage**, **CDN** for delivery, and **feed = hybrid fan-out** (reference the Twitter design rather than repeating it). Back it with the **storage numbers** (hundreds of TB/day).
</Callout>

<Takeaways>
- Uploads: **pre-signed URL → direct to S3 → event → workers** (resize, formats, strip EXIF) → mark ready.
- Delivery: **CDN** with multiple sizes; client picks via `srcset`.
- Metadata in **sharded DB**; likes/comments in a **wide-column store**; counts in **Redis** (sharded counters).
- Feed = **hybrid fan-out** with cached ID lists; images are by far the biggest storage/bandwidth cost.
</Takeaways>
