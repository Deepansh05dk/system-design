<Callout type="problem">
"Show pizza places within 3 km of me, open now, rated 4+." Yelp, Google Maps and Zomato answer this millions of times an hour. Unlike Uber, businesses **don't move** and change rarely, but searches are extremely frequent and must combine **location**, **text** and **filters** quickly.
</Callout>

## Step 1: Requirements

**Functional**
1. Search businesses near a location within a radius (with optional keyword/category, "open now", rating filters).
2. View business details, photos and reviews.
3. Business owners add/update businesses; users write reviews.

**Non-functional**
- Search latency < 200 ms; highly available.
- **Very read-heavy:** searches ≫ business updates (new businesses can take minutes to appear).
- Scale: 200M businesses worldwide, 100K searches/sec at peak.

## Step 2: Estimation

- 200M businesses × ~1 KB metadata = **200 GB**: the location index fits in memory on a handful of machines (replicated for throughput).
- Searches: 100K QPS → spread across replicas; each query touches only a few cells.
- Reviews: billions of rows; read per business, paginated → a separate store.

**Conclusion:** the dataset is **small and static enough to replicate widely**. Read scaling via **replicas + caching** is the main tool; sharding is optional.

## Step 3: Indexing locations

<GeoGrid />

Options (Module 3):
- **Geohash** column with an index: pick precision from the radius (e.g. 6 chars ≈ 1.2 km cells), query the cell + 8 neighbours, then filter exact distance.
- **Quadtree** in memory: adapts to density (Manhattan vs desert), built from the DB periodically; each search server holds a copy.
- **Off-the-shelf:** PostGIS (GiST index), **Elasticsearch geo queries** (combine geo + text + filters + ranking in one query: very practical here).

## Deep dives

**Choosing the cell size from the radius.** Small radius (500 m) → longer geohash (7 chars); large radius (20 km) → shorter (4–5 chars). If too few results, **expand** to the next ring of cells or a coarser precision.

**Quadtree specifics (if you choose it).** Leaves hold ≤ ~100 businesses. Build from the DB on startup (200M businesses takes minutes), keep it **read-only** in memory on every search server, and rebuild/swap periodically or apply small incremental updates. New servers load a snapshot instead of rebuilding.

**Sharding (if the index outgrows memory or for write isolation).** By region is natural, but searches near borders need two shards. Alternatively shard by business ID and **scatter-gather** each search to all shards (each shard has its own geo index): simpler balancing, more fan-out.

**Ranking.** Distance alone isn't enough: combine distance, rating, number of reviews, relevance to the text query, open hours, and personalization (cuisines you like). Usually computed by the search engine's scoring function or a reranking step.

**Reviews and ratings.** Store each review; keep an aggregated `avg_rating` and `review_count` on the business (updated asynchronously) so searches can filter/sort on them without computing averages.

<Callout type="why" title="Yelp vs Uber: why different designs?">
Same core idea (geospatial index), different data behaviour. **Yelp:** static data, read-heavy → index built in batch, **replicated widely**, cached. **Uber:** constantly moving data, write-heavy → **in-memory index updated every few seconds**, sharded by city. Pointing out this contrast in an interview is a great signal.
</Callout>

<Callout type="interview">
Cover: **geospatial index choice** (geohash / quadtree / Elasticsearch geo) with the **cell + neighbours** query, **read-heavy → replicate the index + cache popular cells**, **source-of-truth DB → CDC → index**, **ranking beyond distance**, and **reviews in a separate store with precomputed aggregates**.
</Callout>

<Takeaways>
- Businesses are **static and read-heavy**: build the geo index offline and **replicate** it; cache hot areas.
- Query **cell + neighbours**, pick precision from radius, expand if too few results.
- **Elasticsearch** can combine geo, text, filters and ranking in one query.
- Keep the DB as source of truth; sync the index with **CDC**; precompute rating aggregates.
</Takeaways>
