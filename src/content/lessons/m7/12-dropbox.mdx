<Callout type="problem">
You edit one slide in a 200 MB presentation on your laptop. Seconds later the change appears on your phone and your colleague's computer. Your laptop was offline on a flight for 3 hours while your colleague also edited the same file. When you land, both versions must be handled sensibly. **How does file sync work without re-uploading 200 MB for every small change?**
</Callout>

## Step 1: Requirements

**Functional**
1. Upload and download files; folders.
2. **Sync** automatically across a user's devices.
3. Share files/folders with others (view/edit).
4. File **version history**; restore old versions.
5. Work offline; sync when back online.

**Non-functional**
- **Reliability/durability:** never lose a file (this is the #1 requirement).
- **Efficiency:** minimize bandwidth (mobile data, slow uplinks) and storage.
- Sync latency of a few seconds; consistent view of a folder (no half-synced states visible).
- Scale: 500M users, 50M DAU, average 200 files per user.

## Step 2: Estimation

- 500M users × 200 files × ~1 MB average ≈ **100 PB** of logical data (before dedup and versions).
- 50M DAU × ~10 file changes/day = 500M updates/day ≈ **~6K writes/sec** of metadata.
- Most edits are small changes to existing files → **delta sync** saves most bandwidth.

## Step 3: Key idea: split files into blocks

Instead of treating a file as one blob, split it into **blocks** (e.g. 4 MB), and identify each block by the **hash of its content** (SHA-256). A file becomes a **list of block hashes**.

<ChunkSyncSim />

Wins:
- **Delta sync:** after an edit, only changed blocks are uploaded.
- **Deduplication:** identical blocks (same file uploaded by 1,000 users, or unchanged blocks across versions) are stored **once**.
- **Resumable transfers:** an interrupted upload resumes block by block.
- **Versioning is cheap:** a new version is just a new block list that mostly points to existing blocks.

<Callout type="deep" title="Going deeper: content-defined chunking">
With fixed 4 MB blocks, inserting one byte at the start of a file shifts every block boundary, so every block "changes". **Content-defined chunking** (rolling hash, like rsync's) chooses boundaries based on content, so an insertion only changes the blocks around it. Good to mention for extra depth.
</Callout>

## Step 4: Data model: metadata vs blocks

```text
Metadata DB (strongly consistent, sharded by user/namespace; e.g. MySQL/Postgres):
  files     (file_id, namespace_id, path, latest_version, is_deleted, ...)
  versions  (file_id, version, block_hashes[], size, modified_by, modified_at)
  namespaces/sharing (namespace_id, member_id, permission)
  journal   (namespace_id, seq_no, change)   -- ordered log of changes per folder tree

Block storage (object storage, content-addressed):
  blocks/{sha256} → bytes (compressed, encrypted)
```

Metadata must be **strongly consistent** (it's the source of truth for "what is in my folder"); blocks are **immutable**, so they're trivially cacheable and replicable.

## Deep dives

**Conflicts.** Two devices edit the same file from the same base version while offline. On commit, the server checks the **base version** (optimistic concurrency, Module 3): the first commit wins; the second gets a conflict. Dropbox's choice: keep both, saving the loser as **"file (Asha's conflicted copy).docx"**. Never silently lose data. (Google Docs avoids this for its own format with real-time collaboration (OT/CRDT); see Module 8.)

**The journal.** Each namespace has an ordered change log with sequence numbers. Clients remember the last sequence they've applied; syncing is "give me everything after N". This makes offline catch-up and multiple devices simple and consistent.

**Durability.** Blocks in object storage replicated across zones/regions; metadata DB with synchronous standby + backups. Keep deleted files and old versions for 30+ days (users panic-restore).

**Security & sharing.** Encrypt blocks at rest; permission checks happen in the metadata service (blocks are only fetchable through it or via short-lived signed URLs). Sharing a folder = adding the user to the namespace.

**Large-scale dedup caveat.** Cross-user dedup can leak information ("does someone already have this exact file?") and complicates per-user encryption. Some systems dedup only within a user's own data.

<Callout type="interview">
Essentials: **chunking + content hashing** (delta sync, dedup, resumable), **metadata DB (strongly consistent) vs immutable block storage**, **upload blocks then commit version**, **journal + notification service** for sync, and **conflict handling via base-version checks and conflicted copies**. Mention content-defined chunking for depth.
</Callout>

<Takeaways>
- Files = **lists of content-hashed blocks** → delta sync, dedup, resumable transfers, cheap versions.
- **Metadata** (strongly consistent DB + per-namespace journal) is separate from **immutable blocks** (object storage).
- Flow: **hash → ask what’s missing → upload blocks → commit version → notify → others pull**.
- Conflicts: **optimistic base-version check**, keep a **conflicted copy**, never lose data.
</Takeaways>
