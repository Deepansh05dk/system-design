<Callout type="problem">
HTTP is request → response: the **client always asks first**. But a chat message, a live score or a "your food is out for delivery" update starts on the **server**. How does the server tell the browser something happened, when the browser didn't ask?
</Callout>

## Four techniques

<RealtimeSim />

| Technique | Direction | How | Latency | Server cost | Use for |
|---|---|---|---|---|---|
| **Short polling** | Client → server | Ask every N seconds | Up to N seconds | Many wasted requests | Dashboards refreshed every minute; simple MVPs |
| <Term k="long-polling">**Long polling**</Term> | Client → server (held) | Server holds the request until news or timeout | Low | One pending request per client | Fallback when WebSockets are blocked; older chat systems |
| <Term k="sse">**Server-Sent Events**</Term> | Server → client | One long HTTP response streaming `data:` lines | Low | One open connection per client | Live feeds, notifications, stock tickers, **AI token streaming** |
| <Term k="websocket">**WebSocket**</Term> | **Both ways** | HTTP upgrade to a persistent full-duplex TCP connection | Lowest | One open connection per client | Chat, multiplayer games, collaborative editing, live cursors |

<Callout type="frontend">
- `setInterval(() => fetch('/api/updates'), 3000)` = short polling.
- `new EventSource('/stream')` = SSE (auto-reconnects for free!). ChatGPT-style streaming answers commonly use SSE.
- `new WebSocket('wss://...')` = WebSocket (you handle reconnect + heartbeats yourself, or use Socket.IO).
</Callout>

### How to choose

- **Need the client to send frequent messages too** (chat, games, collaborative editing)? → **WebSocket**.
- **Only server → client updates** (notifications, live scores, progress, streaming text)? → **SSE**: simpler, plain HTTP, works with existing auth/proxies, auto-reconnect.
- **Updates are rare and a delay is fine?** → **polling** is the simplest and most robust.

Other things to handle:
- **Load balancing:** the connection stays on one server, so balance on **connection count** (least connections), not requests.
- **Heartbeats (ping/pong)** every ~30 s to detect dead connections and keep NATs/proxies from closing idle ones.
- **Reconnects:** mobile networks drop constantly. Clients reconnect with **backoff + jitter**, then fetch missed messages since the last message ID they saw. The socket is for speed; the **database is the source of truth**.
- **Deploys:** restarting a WS server drops all its connections → drain gradually so thousands of clients don't reconnect at the same second (thundering herd!).
- **Offline users:** if the user isn't connected, fall back to a **push notification** (APNs/FCM).

<Callout type="interview">
For chat/notifications/live features: "Clients keep a **WebSocket** (or **SSE** if one-way) to a fleet of stateless-ish gateway servers. A **presence store** maps users to servers; messages are routed through **pub/sub**. Messages are persisted first, so on reconnect clients sync from the last seen ID. Offline users get **push notifications**." That's the backbone of WhatsApp, Slack and live comments.
</Callout>

<Takeaways>
- **Polling** (simple, wasteful) → **long polling** (held requests) → **SSE** (server→client stream) → **WebSocket** (two-way).
- Pick **SSE** for one-way updates, **WebSocket** for two-way interaction, **polling** when delays are fine.
- Scaling WebSockets: **sticky connections, presence store (user → server), pub/sub between servers, heartbeats, reconnect with backoff, sync from DB**.
</Takeaways>
