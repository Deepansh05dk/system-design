<Callout type="problem">
Your feed API returns page 2 using `?page=2`. Meanwhile 10 new posts arrived, so page 2 now shows posts the user already saw on page 1. Your mobile app v1.0 is still used by 30% of users, and you need to rename a field. A partner wants to know the instant an order ships, and is polling you 100 times a second. **APIs live a long time. Small design choices decide whether they age well.**
</Callout>

## 1. Pagination

Never return unbounded lists. Two main styles:

Return the cursor in the response, e.g. `{ "items": [...], "nextCursor": "eyJpZCI6OTkxfQ" }`. Make cursors **opaque** (base64-encoded) so clients don't depend on their internals.

<Callout type="frontend">
This is what `useInfiniteQuery`'s `getNextPageParam` consumes. If you've seen duplicate items in an infinite list after new posts arrived, the backend was using offset pagination.
</Callout>

## 2. Versioning

You can't force every mobile user to update. Breaking changes need a new version:
- **URL versioning:** `/v1/orders`, `/v2/orders`. Most common, very explicit.
- **Header versioning:** `Accept: application/vnd.myapi.v2+json` or `API-Version: 2024-10-01` (Stripe uses dated versions).

Better still: **avoid breaking changes**. Adding fields is safe; removing/renaming fields or changing meanings is breaking. Deprecate with warnings and timelines.

## 3. Safe writes

- **Idempotency keys** for POSTs that create things or move money (Module 3).
- **Optimistic concurrency:** return an `ETag`/version with reads; require `If-Match` on updates; reply **409/412** if someone else changed it first.
- **Validation** with clear errors: `400` with a machine-readable body: `{ "error": "invalid_email", "field": "email", "message": "..." }`.

## 4. Webhooks: don't make partners poll

A <Term k="webhook">webhook</Term> is a reverse API: **you** call the **partner's** URL when an event happens (payment succeeded, order shipped).

## 5. The rest of the checklist

- **Consistent naming:** plural nouns (`/orders`), kebab or snake case, consistent JSON field style.
- **Filtering & sorting:** `?status=shipped&sort=-created_at`.
- **Partial responses:** `?fields=id,name` to reduce payloads.
- **Rate limit headers:** `X-RateLimit-Remaining`, `Retry-After`.
- **Long-running work:** return `202 Accepted` + a job URL to poll (or a webhook), instead of holding the request for minutes.
- **Batch endpoints** to avoid chatty APIs over slow networks.

<Callout type="interview">
When you write your API in an interview, include: **cursor pagination** on list endpoints, an **idempotency key** on creation/payment endpoints, and the right **status codes** (201, 202, 409, 429). Example: `GET /v1/users/{id}/feed?cursor=…&limit=20` → `{ items, nextCursor }`. Small details, strong signal.
</Callout>

<Takeaways>
- Use **cursor pagination** for feeds and large lists; offset only for small/jumpable lists.
- **Version** explicitly and prefer **non-breaking** changes.
- Protect writes with **idempotency keys** and **optimistic concurrency** (ETag/If-Match).
- **Webhooks**: queue + signed POST + retries with backoff + event IDs for dedup.
- Use **202 + job status** for long work; good errors; rate-limit headers.
</Takeaways>
