<Callout type="problem">
HTTP is stateless: every request is a stranger. Yet after you log in once, Amazon knows it's you on every page, across thousands of servers and dozens of services. And when you click "Login with Google", a site you've never given a password to somehow gets your name and email. **How does all that work, safely?**
</Callout>

## Two different questions

- **Authentication (AuthN):** *Who are you?* → login, passwords, OTPs, passkeys, "Login with Google". Failure → **401 Unauthorized**.
- **Authorization (AuthZ):** *What are you allowed to do?* → roles and permissions ("admins can delete posts", "you can only edit your own orders"). Failure → **403 Forbidden**.

## After login: sessions vs tokens

Once a user proves who they are, the server gives them something to send with every later request.

### Access token + refresh token

The usual pattern for APIs and mobile apps:
1. On login, the server returns a **short-lived access token** (JWT, ~15 min) and a **long-lived refresh token** (days/weeks, stored server-side so it can be revoked).
2. Every API call sends `Authorization: Bearer <access token>`. Services verify the signature locally: fast, no database.
3. When the access token expires, the client uses the refresh token to get a new one. **Logout / ban** = revoke the refresh token; the access token dies within minutes.

<Callout type="frontend">
**Where to store tokens in the browser?** `localStorage` is readable by any JavaScript on the page, so an XSS bug can steal tokens. An **`HttpOnly`, `Secure`, `SameSite` cookie** can't be read by JS, which is why many teams keep the refresh token (or the session) in such a cookie and the short-lived access token in memory. Cookies then need **CSRF** protection (SameSite + CSRF tokens). You'll be asked this in frontend interviews!
</Callout>

## Auth across microservices

- The **API gateway** validates the token once (signature, expiry) and passes the user ID/roles to services in trusted headers, or services verify the JWT themselves using the public key (JWKS).
- Service-to-service calls use their own identity (**mTLS** or service tokens), so a compromised service can't impersonate users freely.
- **Authorization** stays close to the data: the order service checks "does this order belong to this user?". The gateway can't know that.

### Authorization models

- **RBAC (role-based):** users have roles (admin, editor, viewer); roles have permissions. Simple, common.
- **ABAC (attribute-based):** rules on attributes ("managers can approve expenses < ₹50K in their own department").
- **ReBAC (relationship-based):** permissions follow relationships ("you can edit docs shared with you"). Google Zanzibar, used by Google Drive; open-source: SpiceDB, OpenFGA.

<Callout type="interview">
Typical summary: "Users log in via our auth service (or OAuth/OIDC with Google). We issue a **short-lived JWT access token** and a **revocable refresh token** in an HttpOnly cookie. The **gateway verifies JWTs** and forwards the user ID; each service enforces **ownership/role checks** on its own data. Internal calls use **mTLS**." Mention **401 vs 403** correctly.
</Callout>

<Takeaways>
- **AuthN** = who you are (401). **AuthZ** = what you can do (403).
- **Sessions:** server-side state, easy revocation. **JWTs:** self-contained, verified locally, short-lived + refresh tokens.
- JWT payloads are **readable**; the **signature** prevents tampering.
- **OAuth 2.0 + OIDC (Authorization Code + PKCE)** powers “Login with Google” without sharing passwords.
- In microservices: **verify at the gateway, authorize at the service, mTLS between services**.
</Takeaways>
