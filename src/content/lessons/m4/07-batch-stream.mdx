## MapReduce: the idea behind batch processing

Google's <Term k="mapreduce">MapReduce</Term> (2004) showed how to process petabytes on thousands of cheap machines. The idea is still the foundation of Spark and friends:

<MapReduceSim />

- **Map:** run on each chunk in parallel, where the data lives; emit key/value pairs.
- **Shuffle:** group all values for a key on one machine.
- **Reduce:** combine each key's values.
- If a machine dies, just re-run its piece. The framework handles distribution and failures.

Modern **Spark** keeps intermediate data in memory and offers SQL/DataFrames, so it's much faster and easier than classic Hadoop MapReduce, but the mental model is the same.

## Stream processing concepts

<Term k="stream-processing">Stream processing</Term> introduces new ideas:

- **Windows:** you can't "count all views" of an infinite stream, so you count **per window**: tumbling (every 1 minute), sliding (last 5 min, updated every 10 s), session windows (activity bursts per user).
- **Event time vs processing time:** a phone offline for 10 minutes sends old events late. Do you count them in the window when they *happened* (event time, usually right) or when they *arrived*?
- **Watermarks:** "we're fairly sure all events up to 10:05 have arrived", so the 10:00–10:05 window can be finalized.
- **State:** counts, aggregates and joins are kept in fault-tolerant state stores, checkpointed so a crash doesn't lose them.
- **Exactly-once results:** checkpointing + idempotent/transactional sinks avoid double counting.

- **Lambda architecture:** batch layer (correct) + speed layer (fast), merged at query time. Robust, but you maintain **two codebases** for the same logic.
- **Kappa architecture:** **only streaming**. To recompute, replay the Kafka log through a new version of the stream job. One codebase; relies on long log retention and a capable stream processor.

<Callout type="interview">
Questions like "top K trending hashtags", "ad click aggregation", "YouTube view counts" or "real-time leaderboard of most played songs" are stream processing problems. Say: "Events go to **Kafka**; a **Flink** job aggregates counts in **1-minute tumbling windows by event time**, writing results to Redis/OLAP for serving; raw events are also archived to S3 for **batch reprocessing** and exact billing."
</Callout>

<Takeaways>
- **Batch** = bounded data, high throughput, results later (Spark, MapReduce, warehouses).
- **Stream** = unbounded events, results in seconds (Kafka Streams, Flink).
- MapReduce: **map → shuffle → reduce**, run in parallel where data lives.
- Streams need **windows, event time, watermarks, state and checkpoints**.
- **Lambda** = batch + speed layers; **Kappa** = streaming only with replay.
</Takeaways>
