<Callout type="problem">
Your shop has 20 million products. A user types "red running shoes". You try `SELECT * FROM products WHERE title LIKE '%red%' AND title LIKE '%running%' ...`. It takes 12 seconds, it can't rank results by relevance, it misses "Running Shoe – Red", and a typo like "runing" finds nothing. **How do Amazon and Google search instantly?**
</Callout>

## Why normal indexes don't help

A B-tree index is sorted by the **whole value** from the start. It helps `LIKE 'red%'` (prefix) but not `LIKE '%shoes%'` (a word in the middle). The database is back to scanning every row.

## The inverted index

An <Term k="inverted-index">inverted index</Term> flips the problem around. Instead of "document → words", it stores **"word → list of documents containing it"**. Exactly like the index at the back of a textbook.

<InvertedIndexDemo />

To search "red running shoes": fetch the list for `red`, the list for `running`, the list for `shoes`, then combine and rank them. Each lookup is a fast key lookup, no matter how many documents exist.

## What a search engine adds on top

1. **Tokenizing:** split text into words.
2. **Normalizing:** lowercase, remove accents, drop stop words ("the", "for").
3. **Stemming:** "running", "runs", "ran" → "run".
4. **Synonyms:** "tee" ↔ "t-shirt".
5. **Fuzzy matching:** "runing" still finds "running" (edit distance).
6. **Relevance scoring:** BM25 / TF-IDF. Rare words count more than common ones; matches in the title count more than in the description. Plus business signals like popularity and rating.
7. **Facets & filters:** "Brand: Nike (120), Size: 9 (45)".

## Where search fits in a system

Search engines like **Elasticsearch** or **OpenSearch** are usually **not** the source of truth. The main database is. The search index is a **derived copy** kept in sync:

<Callout type="why" title="Why not write to both the DB and Elasticsearch directly from the app?">
"Dual writes" break easily: if the DB write succeeds and the Elasticsearch write fails (or the app crashes in between), they disagree forever. Capturing changes **from the database's log** (CDC) or using an **outbox table** guarantees every committed change eventually reaches the index.
</Callout>

<Callout type="frontend">
The search box in your app is the frontend half of this. Debouncing keystrokes, showing results while typing (typeahead) and highlighting matched words all build on what the search engine returns. We'll design a full **Typeahead / Autocomplete** system in Module 7.
</Callout>

<Callout type="interview">
Whenever a design has a search box ("search tweets", "search products", "search restaurants by name"), say: **"Full-text search goes to Elasticsearch, fed asynchronously from the primary DB via CDC/Kafka. The search index is eventually consistent, which is acceptable here."**
</Callout>

<Takeaways>
- B-tree indexes can't find words in the middle of text; **inverted indexes** map word → documents.
- Search engines add **stemming, fuzzy matching, ranking (BM25) and facets**.
- Search is a **derived store**, synced from the source of truth via **CDC / events**. Avoid dual writes.
</Takeaways>
