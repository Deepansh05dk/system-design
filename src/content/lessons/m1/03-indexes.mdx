<Callout type="problem">
Your users table has 50 million rows. The login query `SELECT * FROM users WHERE email = 'asha@mail.com'` takes **4 seconds**. Your CPU is fine, your disk is fine. Adding a single line, `CREATE INDEX ON users(email)`, brings it down to **2 milliseconds**. **What just happened?**
</Callout>

## The phone book idea

Without an index, the database must look at **every row** to find matching emails. That's a **full table scan**.

An <Term k="index">index</Term> is a separate, **sorted** structure that maps a column's values to where the rows live. Like the index at the back of a book: to find "TCP", you don't read the whole book, you look up "T" in the index and jump to page 214.

## How a B-tree index works

Most database indexes are <Term k="btree">B-trees</Term> (more precisely B+ trees):

- Keys are kept **sorted**.
- Each node is a disk **page** holding hundreds of keys, so the tree is very **wide and shallow**.
- To find a key you go root → branch → leaf: just **3–4 page reads** even for billions of rows.
- Because keys are sorted, the same index also speeds up **range queries** (`WHERE created_at > '2026-01-01'`), **sorting** (`ORDER BY`) and **prefix matches** (`LIKE 'ash%'`).

<Callout type="analogy">
A library: the B-tree root says "A–F: floor 1, G–M: floor 2...". Each floor has a sign for each aisle, each aisle for each shelf. Three signs and you're at the right book, whether the library has a thousand books or a billion.
</Callout>

## Indexes are not free

**Rule of thumb:** index the columns you **filter, join or sort by often**. Don't index everything. A write-heavy table (like a log of events) should have few indexes.

## Composite indexes and column order

An index can cover several columns: `CREATE INDEX ON orders(user_id, created_at)`.

It's sorted by `user_id` first, then by `created_at` within each user. So it helps:
- ✅ `WHERE user_id = 7`
- ✅ `WHERE user_id = 7 ORDER BY created_at DESC LIMIT 20` (perfect: "a user's latest orders")
- ❌ `WHERE created_at > '2026-01-01'` alone (the index isn't sorted by date first)

This is the **leftmost prefix rule**. It's like a phone book sorted by last name, then first name: great for "all Sharmas", useless for "everyone named Priya".

## Other index types (good to know)

| Type | Good for |
|---|---|
| **Hash index** | Exact equality lookups only (`=`), no ranges |
| **Full-text / inverted index** | Searching words inside text (lesson 8) |
| **Geospatial (R-tree, GiST)** | "Restaurants within 2 km" (Module 3) |
| **LSM tree** (used by Cassandra, RocksDB) | Very fast writes: buffer in memory, flush sorted files to disk, merge in the background |

<Callout type="deep" title="Going deeper: B-tree vs LSM tree">
**B-trees** update data in place: great for reads, OK for writes. **LSM trees** (Log-Structured Merge trees) turn all writes into fast sequential appends and merge files later ("compaction"). That's why write-heavy databases like Cassandra, ScyllaDB and RocksDB use LSM trees, while PostgreSQL and MySQL use B-trees. Interview phrase: "write-heavy workload → an LSM-based store like Cassandra."
</Callout>

<Callout type="interview">
When you design a table in an interview, **mention the index** that serves the main query: "The main query is 'a user's latest 20 orders', so I'd add an index on `(user_id, created_at DESC)`." This shows you think about how data is read, not just how it's stored.
</Callout>

<Takeaways>
- Without an index → **full table scan** (O(N)). With a B-tree index → a few page reads (O(log N)).
- B-trees keep keys sorted, which also helps **ranges and sorting**.
- Indexes **speed reads but slow writes** and use space. Index what you query.
- Composite indexes follow the **leftmost prefix rule**: order the columns to match your queries.
</Takeaways>
