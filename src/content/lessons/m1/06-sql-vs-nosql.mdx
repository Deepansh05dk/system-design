<Callout type="problem">
"Which database would you use?" comes up in **every** system design interview. There's rarely one right answer, but there are definitely **wrong reasons**. Let's build a framework you can apply in 30 seconds.
</Callout>

## Start from the access pattern, not the brand

Ask these questions about the data:

1. **What are the main reads and writes?** (by ID? by user, sorted by time? complex filters?)
2. **How much data and traffic?** Read-heavy or write-heavy?
3. **What consistency is needed?** Is a stale read okay for a few seconds? Is money involved?
4. **How related is the data?** Lots of JOINs, or self-contained records?
5. **How stable is the structure?** Fixed fields or wildly varying?

## Common real-world pairings

| Feature | Typical choice | Why |
|---|---|---|
| Users, accounts, orders, payments | PostgreSQL / MySQL | Relations + transactions |
| Sessions, cache, rate-limit counters | Redis | Key lookup, in-memory speed, TTLs |
| Chat messages, activity feeds | Cassandra / ScyllaDB / DynamoDB | Write-heavy, read by partition + time |
| Product catalog | MongoDB or Postgres with JSONB | Varying attributes |
| Search box | Elasticsearch / OpenSearch | Full-text ranking |
| Friend recommendations | Graph DB (or precomputed in batch jobs) | Multi-hop relationships |
| Metrics / monitoring | Prometheus, TimescaleDB, InfluxDB | Time-series |
| Images, videos, files | Object storage (S3) | Big blobs, cheap, durable |

Large systems use **several** of these at once. This is called **polyglot persistence**: use the right store for each job.

<Callout type="why" title="Modern blur: the lines are fading">
PostgreSQL has JSONB (documents) and full-text search. MongoDB has multi-document ACID transactions. "NewSQL" / distributed SQL databases (Google Spanner, CockroachDB, YugabyteDB, TiDB) give SQL + ACID **and** horizontal scaling, at the cost of higher write latency and operational complexity. In interviews, it's fine to mention these as an option when you need both SQL guarantees and global scale.
</Callout>

## A sample interview answer

> "For **orders and payments** I'll use **PostgreSQL**: we need transactions so we never charge without creating an order, and the support team needs flexible queries. At our scale (~2K writes/sec), one primary with read replicas is enough. Later we can shard by `user_id`.
>
> For the **activity feed** I'll use **Cassandra**: it's write-heavy, each user's feed is read newest-first, and we never JOIN it. Partition key `user_id`, clustering key `created_at DESC`.
>
> **Sessions** go in **Redis** with a TTL."

Notice each choice has a **because**.

<Callout type="mistake">
Avoid: "NoSQL because it scales" (so does sharded SQL), "MongoDB because it's schemaless" (you still have a schema, just in your code), "SQL because I know it" (fine in real life, weak in an interview). Tie the choice to **access pattern, consistency and scale**.
</Callout>

<Takeaways>
- Decide from **access patterns, consistency needs, scale and relationships**, not from popularity.
- **Default to relational** for core business data; reach for NoSQL when a specific pattern needs scale or flexibility.
- Real systems are **polyglot**: several stores, each with a clear reason.
</Takeaways>
