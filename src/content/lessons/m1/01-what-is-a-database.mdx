<Callout type="problem">
You build a to-do app. You save tasks in a `tasks.json` file on the server. It works great for you. Then 10,000 users sign up. Two users save at the same moment and one user's change disappears. The server crashes mid-write and the file is corrupted. Finding "all tasks due today" means reading the whole 2 GB file. **What went wrong?**
</Callout>

A plain file is fine for one user. A <Term k="database">database</Term> is software built to solve exactly these problems when **many users** read and write **lots of data** at the same time.

## What a database gives you

| Problem with a plain file | What a database does |
|---|---|
| Two people write at once → one change is lost | **Concurrency control:** safely handles thousands of simultaneous readers and writers |
| Crash halfway through a write → corrupted data | **Durability & crash recovery:** a write-ahead log lets it recover to a correct state |
| Finding something = reading everything | **Indexes:** jump straight to the rows you need |
| You write custom code for every question | **Query language:** ask questions like "orders over ₹1000 this week" in one line |
| Anyone with the file can change anything | **Access control** and **constraints** (e.g. email must be unique) |
| Data outgrows one disk | **Replication and partitioning** (in many databases) |

<Callout type="frontend">
You've used storage in the browser: `localStorage` is basically a tiny key-value store, and **IndexedDB** is a real (small) database with transactions and indexes. Server databases are the same idea but built for millions of users, terabytes of data and crash safety.
</Callout>

That write-ahead log idea shows up everywhere in system design: replication streams the log to other machines, and Kafka is basically "a log as a product".

## Vocabulary you'll need

- **Table / collection:** a group of similar records (users, orders).
- **Row / record / document:** one item (one user).
- **Column / field:** one attribute (email).
- <Term k="schema">**Schema**</Term>: the structure: which fields exist and their types.
- **Query:** a request to read or change data.
- <Term k="primary-key">**Primary key**</Term>: a field that uniquely identifies each record (`id`).
- <Term k="index">**Index**</Term>: a lookup structure to find records fast (next lessons).
- <Term k="transaction">**Transaction**</Term>: a group of changes that succeed or fail together.

<Callout type="interview">
In almost every design interview you will be asked **"which database would you use and why?"** The worst answer is a name without a reason ("MongoDB because it scales"). The best answers connect the choice to the **access pattern**: "Orders need transactions and we query them in many ways, so PostgreSQL. Session data is only looked up by session ID, so Redis." The next lessons give you the reasons.
</Callout>

<Takeaways>
- Databases solve **concurrency, durability, fast lookup, querying and scale**, the things plain files can't.
- Inside: a **query planner**, a **buffer pool** (RAM cache of pages), a **write-ahead log** (for crash safety) and **data files** on disk.
- Two families: **relational (SQL)** and **NoSQL**. Choose based on how your data is accessed.
</Takeaways>
