<Callout type="problem">
To show a feed of 50 posts, you need each post's text, the author's name and avatar, the like count and the comment count. In a "clean" database that's a JOIN across 4 tables, for every feed load, for millions of users. **Should we copy the author's name into every post to skip the JOIN? What happens when the author changes their name?**
</Callout>

## Normalization: every fact in one place

<Term k="normalization">Normalization</Term> means organizing data so each fact is stored **exactly once**, and everything else refers to it by ID. The customer's email lives in the `customers` table only; orders just store `customer_id`.

## Denormalization: copy for speed

<Term k="denormalization">Denormalization</Term> means **deliberately duplicating** data so reads don't need JOINs or extra lookups: copy the author's name into each post, keep a `like_count` column instead of counting rows in `likes` every time.

## Common denormalization patterns you'll use in designs

1. **Counters:** store `like_count` on the post and increment it, instead of `COUNT(*)` over millions of likes per page view.
2. **Precomputed feeds:** store each user's timeline as a ready list of post IDs (the "fan-out on write" idea in the News Feed design).
3. **Embedded snapshots:** an order stores the **price at the time of purchase**. This is actually *correct* duplication: if the product price changes later, the old order must not change!
4. **Read models:** a separate store optimized for reading (search index, cache, materialized view), updated from the main database. This is the idea behind **CQRS** (Module 4).

<Callout type="tip">
Not all duplication is bad. Ask: **"If the original changes, should the copy change too?"** Author name on a post: yes, so you need a way to update copies (or accept a delay). Price on an old invoice: no, the copy is a historical record.
</Callout>

## How to keep copies in sync

- **In the same transaction** (only if everything is in one database).
- **Asynchronously with events:** "user renamed" event → a background worker updates copies. Copies are stale for a few seconds (eventual consistency).
- **Don't copy, cache:** keep data normalized and put a **cache** in front of the slow read. The cache is a temporary copy that expires (TTL) or is invalidated.

<Callout type="interview">
A strong pattern: **"Source of truth is normalized in PostgreSQL. For the hot read path, I'll denormalize into a cache / read store, updated asynchronously. A few seconds of staleness is acceptable for this feature."** Always state **what's the source of truth** and **how stale copies can be**.
</Callout>

<Takeaways>
- **Normalize** for correctness and simple writes; **denormalize** for fast reads.
- Denormalization moves work from **read time to write time**, and adds the job of keeping copies in sync.
- Keep a clear **source of truth**; treat copies (caches, counters, feeds, search indexes) as derived data.
</Takeaways>
