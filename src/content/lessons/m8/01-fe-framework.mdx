<Callout type="problem">
"Design the Facebook news feed" means something very different in a **frontend** round. Nobody wants your Cassandra schema. They want to know how you'd structure components, manage state, talk to the API, paginate, cache, handle errors and make it fast and accessible on a cheap Android phone. Same question, different lens.
</Callout>

## What's different in a frontend round

| Backend round | Frontend round |
|---|---|
| Databases, sharding, queues | Component architecture, state management |
| Service-to-service APIs | Client ↔ server API design (what the UI needs) |
| Throughput, replication | Rendering performance, bundle size, network usage |
| Server failures | Offline, flaky networks, error and loading states |
| Data consistency across nodes | Consistency between client cache and server (optimistic updates) |
| — | Accessibility, i18n, UX details |

Typical prompts: news feed, autocomplete/typeahead, chat UI, image carousel/gallery, Google Docs-style editor, e-commerce product page, video player, Google Sheets, Figma-like canvas, poll widget, infinite scroll, a design system / component library.

### R: Requirements (~5 min)
- **Functional:** core features (e.g. feed: view posts, like, comment, infinite scroll, create post).
- **Non-functional:** devices (mobile web? desktop?), network conditions, performance targets (Core Web Vitals), accessibility, i18n, offline support, SEO needs.
- Scope: which parts are you designing? Just the feed list? The composer too?

### A: Architecture (~10 min)
Draw the **client-side architecture**: views/components, a **client store** (server-state cache vs UI state), a **data/API layer**, and the server/BFF. Explain the responsibility of each and how data flows.

```text
Server (API / BFF) ⇄ API client layer (fetch, retries, normalization)
                    ⇄ Client store (server-state cache: React Query / Apollo / Redux)
                    ⇄ Components (Feed → FeedItem → MediaGallery, ActionBar, Comments)
```

Also choose a **rendering strategy** (CSR / SSR / SSG / streaming / islands); next lesson.

### D: Data model (~5 min)
- **Server data** the client caches (posts, users, comments). Normalize by ID? (`posts: {id: post}`, `users: {id: user}`) so a user's name updates everywhere.
- **Client-only state:** UI state (open menus, drafts), form state, URL state (filters in the query string).
- Where each piece lives and who owns it.

### I: Interface (~10 min)
- **Client ↔ server API:** endpoints and payload shapes the UI needs (`GET /feed?cursor=…` returning posts + embedded authors + nextCursor), REST vs GraphQL, real-time channel (SSE/WebSocket) for new items.
- **Component APIs:** props of key components (`<Autocomplete onSelect fetchSuggestions debounceMs renderItem />`).

### O: Optimizations & deep dives (~15 min)
Pick what matters for this product: performance (virtualization, code splitting, image loading, caching), network (pagination, prefetch, batching), **optimistic updates**, error/loading/empty states, **offline**, **accessibility** (keyboard, screen readers, focus management), **i18n** (RTL, pluralization), security (XSS, CSP), and observability (RUM, error tracking).

<Callout type="frontend">
This is your home turf. The backend knowledge from this course is your **advantage**: you can explain *why* the API should use cursor pagination, *why* a CDN serves your images, and *what* the server does when you send an idempotency key. Frontend candidates who can talk across the stack stand out.
</Callout>

<Callout type="interview">
Make your client architecture diagram as explicit as a backend one. Say **where state lives** and **why** (server cache vs UI state vs URL), and always cover **loading, error, empty and offline states**. Interviewers notice when candidates only design the happy path.
</Callout>

<Takeaways>
- Frontend rounds focus on **components, state, client–server API, performance, UX and accessibility**.
- **RADIO:** Requirements → Architecture → Data model → Interface → Optimizations.
- Separate **server state (cached)** from **UI state** and **URL state**; normalize shared entities.
- Always handle **loading / error / empty / offline**, and mention **accessibility**.
</Takeaways>
