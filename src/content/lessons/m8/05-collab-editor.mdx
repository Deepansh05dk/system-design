<Callout type="problem">
Five people edit the same Google Doc at the same time. Everyone sees others' cursors and changes within a fraction of a second. Two people type in the same sentence simultaneously, and everyone still ends up with the **same** document. Someone on a train edits offline for an hour and it merges cleanly when they reconnect. **How do concurrent edits not destroy each other?**
</Callout>

## Requirements

**Functional:** real-time co-editing of rich text; see collaborators' cursors/selections and presence; undo/redo per user; version history; comments; offline editing that syncs later.

**Non-functional:** local typing must feel **instant** (never wait for the server); changes appear for others in < 1 s; all copies **converge** to the same document; no lost edits; scale to many documents (each with a handful to ~100 editors).

## The core problem: concurrent edits

Each user edits their **local copy** immediately (local-first, so typing never lags), then sends **operations** like "insert 'x' at position 5" to others. But positions change when someone else edits earlier in the text at the same time:

<Term k="crdt">CRDTs</Term> avoid position shifting by giving every character a **unique, stable ID** and inserting "after character ID X" instead of "at index 5". <Term k="ot">OT</Term> keeps simple indexes but rewrites operations to account for what happened concurrently.

With CRDTs (e.g. Yjs), the server can be simpler: it relays and stores updates (or a merged state) without transforming, and peers can even sync directly.

## Deep dives

**Undo/redo.** Must be **per user**: Ctrl+Z undoes *my* last change, not my colleague's. Implemented as inverse operations (transformed like any other op).

**Offline.** Queue local ops (persist in IndexedDB); on reconnect, send them with their base revision. OT rebases them on the server; CRDTs merge naturally. Long offline sessions favor CRDTs.

**Permissions.** Check on connect and on every op (view vs comment vs edit). Revoking access closes the socket.

**Scaling.** Each document is small and hot only while being edited: route each doc to one session server (sharded by doc ID), keep active docs in memory, evict idle ones. Millions of documents scale horizontally because they're independent.

**Rich text.** Edits are not just characters: formatting ranges, lists, tables, embedded images. Editors like ProseMirror, Tiptap, Lexical and Slate model the document as a tree with OT/CRDT bindings (y-prosemirror, etc.).

<Callout type="frontend">
This is one of the most frontend-heavy system designs: the **client holds the source of truth for what the user sees**, applies changes optimistically, rebases remote changes, renders remote cursors without jank (throttle presence, use CSS transforms), and keeps everything accessible. Mentioning ProseMirror/Yjs shows practical awareness.
</Callout>

<Callout type="interview">
Key points: **local-first edits + operations over WebSocket**, **convergence via OT (server orders/transforms) or CRDTs (commutative merges)**, **one session owner per document**, **append-only op log + snapshots**, **separate ephemeral presence channel**, **per-user undo**, and **offline queue**. Be ready to explain the position-shifting example.
</Callout>

<Takeaways>
- Apply edits **locally first**; send **operations**, not whole documents.
- Concurrent edits need **OT** (transform positions; usually server-ordered) or **CRDTs** (unique IDs, automatic merge, offline-friendly).
- Route each document to **one session**; store an **op log + snapshots**.
- **Presence/cursors** are ephemeral and throttled; **undo is per user**.
</Takeaways>
