<Callout type="problem">
There are billions of devices on the internet. When your browser wants to talk to Netflix, how does the message know **which machine** to go to? And once it gets there, how does it know **which program** on that machine should handle it?
</Callout>

Two ideas answer this: **IP addresses** (which machine) and **ports** (which program on the machine). A third, **DNS**, lets humans use names instead of numbers.

## IP address: the machine's postal address

Every device connected to a network gets an <Term k="ip">IP address</Term>. Routers on the internet read the destination IP and pass the message along, hop by hop, until it reaches that machine, just like the postal system reads a pin code and city.

| Version | Example | How many addresses | Notes |
|---|---|---|---|
| IPv4 | `142.250.183.14` | ~4.3 billion (2³²) | Four numbers 0–255. We ran out long ago. |
| IPv6 | `2404:6800:4009:82b::200e` | 2¹²⁸ (practically unlimited) | Slowly replacing IPv4. |

### Public vs private IPs

Your laptop at home probably has an IP like `192.168.1.5`. That's a **private** IP that works only inside your home network. Your router has one **public** IP that the internet sees, and it translates between them (this is called **NAT**, Network Address Translation).

<Callout type="analogy">
A big office building has one street address (the public IP). Inside, each desk has an internal extension number (the private IP). The receptionist (router/NAT) knows which desk to route each delivery to.
</Callout>

In system design this matters because your servers inside a data center usually have **private IPs**. Only the load balancer (or gateway) has a public IP. This hides your servers and makes them safer.

## Ports: which program on the machine?

One server can run many programs at the same time: a web server, a database, an SSH service. A <Term k="port">port</Term> is a number (0–65535) that tells the machine **which program** should get the incoming data.

An address is really **IP + port**, e.g. `54.239.28.85:443`.

| Port | Used by |
|---|---|
| 80 | HTTP (plain web) |
| 443 | HTTPS (secure web) |
| 22 | SSH (remote login) |
| 5432 | PostgreSQL database |
| 3306 | MySQL database |
| 6379 | Redis cache |
| 27017 | MongoDB |

<Callout type="frontend">
When you run `npm run dev` and open `http://localhost:5173`, `localhost` is the IP `127.0.0.1` (your own machine) and `5173` is the port your dev server listens on. Running two dev servers? They need different ports, because only one program can listen on a given port.
</Callout>

## DNS: the internet's phone book

Humans remember `netflix.com`; machines need `54.155.178.5`. <Term k="dns">DNS</Term> (Domain Name System) translates names to IP addresses.

DNS is not one server. It's a **hierarchy** spread across the world, so no single machine has to know every domain. Step through a lookup for `www.netflix.com`:

### DNS caching and TTL

A full lookup can take 100+ ms, so DNS answers are **cached at every level**: browser, operating system, router and resolver. Each record has a **TTL**. Short TTL (e.g. 60 s) means changes spread quickly but more lookups happen. Long TTL (e.g. 1 day) means fewer lookups, but if you change your server's IP, some users keep going to the old one until their cache expires.

<Callout type="why" title="Why this matters in system design">
DNS is often the **first** layer of load balancing and failover:
- **DNS load balancing:** return different IPs to different users (round robin) so traffic spreads across servers or data centers.
- **GeoDNS:** return the IP of the data center closest to the user (users in India get the Mumbai IP, users in the US get the Virginia IP).
- **Failover:** if a data center dies, update DNS to point elsewhere. But TTL caching means some users are stuck for a while, which is why DNS failover is **slow** compared to a load balancer.
</Callout>

### Common DNS record types

| Record | Maps | Example |
|---|---|---|
| A | name → IPv4 | `netflix.com → 54.155.178.5` |
| AAAA | name → IPv6 | `netflix.com → 2a05:d018:...` |
| CNAME | name → another name (alias) | `www.shop.com → shop.vercel-dns.com` |
| MX | domain → mail server | `gmail.com → smtp.google.com` |
| NS | domain → its name servers | `netflix.com → ns-81.awsdns-10.com` |

<Callout type="frontend">
When you deploy a site to Vercel or Netlify and add a custom domain, they ask you to add a **CNAME** or an **A record**. Now you know why: you're telling DNS "my name points to their servers".
</Callout>

<Callout type="interview">
You rarely design DNS itself, but you **use** it in designs. Good phrases: "We'll use **GeoDNS** to route users to the nearest region." "DNS-based failover is slow because of TTL caching, so inside a region we rely on load balancers for fast failover."
</Callout>

<Takeaways>
- **IP address** = which machine. **Port** = which program on that machine. Together: `IP:port`.
- Servers in a data center usually have **private IPs**; only the entry point (load balancer) is public.
- **DNS** turns names into IPs using a hierarchy: resolver → root → TLD → authoritative.
- DNS answers are **cached using TTL**. Great for speed, bad for fast failover.
- DNS can do simple load balancing and **geo-routing**.
</Takeaways>
