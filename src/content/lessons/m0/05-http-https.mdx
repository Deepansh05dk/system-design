<Callout type="problem">
TCP gives us a reliable pipe of bytes, but the bytes need a **meaning**. How does a server know you want a product page and not to delete your account? How does a browser know the response is JSON, or that it can cache it for 60 seconds? And how do we stop someone on the café Wi-Fi from reading your password?
</Callout>

<Term k="http">HTTP</Term> gives the bytes meaning. <Term k="https">HTTPS</Term> adds encryption. As a frontend dev you use HTTP daily. This lesson fills in the parts that matter for **designing systems**.

## The shape of HTTP

HTTP is **request → response**. The client always starts. A request has:
- a **method** (what to do): GET, POST, PUT, PATCH, DELETE
- a **path** (on what): `/api/products/42`
- **headers** (extra info): auth tokens, content type, caching hints
- an optional **body** (data): JSON, form data, a file

The response has a **status code**, headers, and a body. Play with it:

### Two properties interviewers love

- **Safe:** doesn't change anything on the server (GET, HEAD).
- **Idempotent:** doing it once or 10 times has the **same end result** (GET, PUT, DELETE). POST is **not** idempotent: send "create order" twice and you get two orders.

<Callout type="why" title="Why idempotency matters">
Networks fail. A client sends a request, the connection drops, and the client doesn't know if the server got it. **Should it retry?** For GET/PUT/DELETE, yes, it's safe. For POST (like "pay ₹500"), a retry could charge twice! We'll fix this with **idempotency keys** in Module 3.
</Callout>

## HTTP is stateless

Each HTTP request is independent. The server doesn't automatically remember your previous request. To build "logged-in" experiences, we send identity with **every** request, using cookies or tokens in headers.

This "statelessness" is a gift for scaling: if no server needs to remember you, **any server can handle any request**, so we can add servers freely behind a load balancer.

## Caching headers (huge for performance)

| Header | What it does |
|---|---|
| `Cache-Control: max-age=3600` | "You may reuse this for 1 hour without asking me." |
| `Cache-Control: no-store` | "Never cache this" (bank pages). |
| `ETag: "a1b2c3"` | A fingerprint of the content. The browser can later ask `If-None-Match: "a1b2c3"` and get a tiny **304 Not Modified** if nothing changed. |
| `Cache-Control: public, s-maxage=600` | CDNs (shared caches) may keep it for 10 minutes. |

CDNs and browsers rely on these headers. Good headers mean fewer requests reach your servers at all.

## HTTP/1.1 vs HTTP/2 vs HTTP/3

| | HTTP/1.1 (1997) | HTTP/2 (2015) | HTTP/3 (2022) |
|---|---|---|---|
| Transport | TCP | TCP | QUIC (on UDP) |
| Format | Plain text | Binary frames | Binary frames |
| Requests per connection | One at a time (browsers open ~6 connections per domain) | **Many in parallel** (multiplexing) | Many in parallel, and independent |
| Header compression | No | Yes (HPACK) | Yes (QPACK) |
| Head-of-line blocking | Yes (per connection) | Fixed at HTTP level, still at TCP level | Fixed |

<Callout type="frontend">
Remember bundling all JS into one file and making image sprites? That was mostly a workaround for HTTP/1.1's "one request at a time per connection" limit. With HTTP/2 multiplexing, many small files are much less costly. That's also why domain sharding (cdn1, cdn2, cdn3...) is an outdated trick.
</Callout>

## HTTPS and TLS: how the padlock works

HTTPS = HTTP inside a <Term k="tls">TLS</Term> tunnel. TLS gives three guarantees:

1. **Encryption:** nobody in the middle can read the data.
2. **Integrity:** nobody can change the data without being detected.
3. **Authentication:** you're really talking to `bank.com`, proven by a **certificate** signed by a trusted Certificate Authority (CA).

<Callout type="deep" title="Going deeper: asymmetric vs symmetric encryption">
**Asymmetric** (public/private key) crypto is used during the handshake to agree on a secret safely and to verify the certificate. It's slow. **Symmetric** crypto (one shared key, like AES) is used for the actual data because it's very fast. TLS uses the slow one only to set up the fast one.
</Callout>

### TLS termination

Decrypting TLS costs CPU. In most designs, the **load balancer terminates TLS**: it decrypts incoming HTTPS and forwards plain HTTP to app servers inside the private network (or re-encrypts if security rules require it). This keeps certificates in one place and frees app servers from crypto work.

<Callout type="interview">
In designs, write the client → load balancer arrow as **HTTPS** and say "TLS terminates at the load balancer." When a design involves retries, mention which endpoints are **idempotent**. These small details show maturity.
</Callout>

<Takeaways>
- HTTP = method + path + headers + body → status + headers + body. It's **stateless**, which makes horizontal scaling easy.
- Know your status code families: **2xx ok, 3xx redirect/cache, 4xx client error, 5xx server error**. Especially 301/302, 304, 401/403, 429, 503.
- **Idempotent** methods (GET, PUT, DELETE) are safe to retry; **POST is not**.
- **Caching headers** (Cache-Control, ETag) let browsers and CDNs skip your servers.
- HTTP/2 multiplexes requests on one connection; HTTP/3 runs on QUIC (UDP).
- **TLS** gives encryption, integrity and authentication, usually **terminated at the load balancer**.
</Takeaways>
