<Callout type="problem">
The internet is messy. Data is split into small <Term k="packet">packets</Term>, and each packet may take a different route. Some arrive late, some arrive out of order, some never arrive at all. A bank transfer can't lose a single byte. A video call can't wait for a lost frame from 2 seconds ago. **How do we handle both needs?**
</Callout>

Two transport <Term k="protocol">protocols</Term> give two different answers: **TCP** and **UDP**.

## TCP: the careful courier

<Term k="tcp">TCP</Term> (Transmission Control Protocol) promises:

1. **Reliable:** every packet arrives. Lost ones are detected and **resent**.
2. **Ordered:** packets are numbered (sequence numbers) and put back in order.
3. **Connection-based:** both sides agree to talk first (the handshake).
4. **Flow & congestion control:** it slows down if the receiver or network is overwhelmed.

<Callout type="why" title="Why does the handshake matter for system design?">
Each new TCP connection costs a round trip (plus more for TLS). From India to a US server that's ~200 ms **before any data**. This is why we:
- **Reuse connections** (HTTP keep-alive, connection pooling to databases)
- Put servers and CDNs **closer to users**
- Use newer protocols like **HTTP/3 (QUIC)**, which combine handshakes
</Callout>

## UDP: the fire-and-forget postcard

<Term k="udp">UDP</Term> (User Datagram Protocol) just sends packets. No handshake, no acknowledgements, no resending, no ordering. If a packet is lost, it's gone. If order matters, the application has to deal with it.

That sounds bad, but it's exactly what some apps want: **speed over perfection**.

<Callout type="analogy">
**TCP** is a phone call: you dial, the other side picks up, and if they miss a word they say "sorry, repeat that?" **UDP** is shouting across a crowded room: fast, but if they missed a word, you're already on the next sentence.
</Callout>

Why is a video call on UDP? If a video frame from 200 ms ago is lost, resending it is useless because the conversation has moved on. Better to show the next frame. A small glitch beats a frozen screen.

<Callout type="deep" title="Going deeper: QUIC and HTTP/3">
**QUIC** is a newer protocol built **on top of UDP** that adds reliability, encryption and multiple independent streams in user space. HTTP/3 runs on QUIC. It fixes TCP's head-of-line blocking (one lost packet doesn't stall unrelated streams) and combines the connection + TLS handshake into fewer round trips. Google, YouTube and Cloudflare already use it widely.
</Callout>

<Callout type="interview">
Typical prompts: "Design a video calling app" or "Design a multiplayer game". Say **UDP (or WebRTC, which uses UDP) for real-time media**, but **TCP for chat messages, signaling and payments**. Showing you'd use **both** in the same system is a strong signal.
</Callout>

<Takeaways>
- **TCP** = reliable, ordered, connection-based. Costs a handshake and can stall on lost packets.
- **UDP** = fast, simple, no guarantees. Good when fresh data matters more than complete data.
- Most web traffic (HTTP/1.1, HTTP/2, databases) uses TCP. Real-time media and games use UDP. HTTP/3 uses QUIC over UDP.
- Connection setup costs round trips → **reuse connections** and **move servers closer to users**.
</Takeaways>
