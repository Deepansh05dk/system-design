<Callout type="problem">
You type `www.amazon.com` and press Enter. About half a second later, a full page appears. In that half second your request travelled across cities, maybe across oceans, touched dozens of machines, and came back. **What actually happened?**
</Callout>

This is the most famous "warm-up" question in interviews. It's also the best way to start this course, because every step of the journey is a topic we'll study later. Think of this lesson as the **map of the whole course**.

## The cast of characters

Before the journey, let's meet the main players. Don't worry if some of these are new. We'll cover each one in detail later.

| Player | What it is | Analogy |
|---|---|---|
| <Term k="client">Client</Term> | Your browser (or mobile app). It **asks** for things. | A customer in a restaurant |
| <Term k="server">Server</Term> | A computer that **answers** requests. It's just a normal computer running a program that waits for messages. | The kitchen |
| <Term k="dns">DNS</Term> | Turns a name (`amazon.com`) into a numeric address (an <Term k="ip">IP address</Term>). | The phone book |
| <Term k="load-balancer">Load balancer</Term> | Spreads requests across many servers. | The host who seats you at a free table |
| <Term k="cdn">CDN</Term> | Servers all over the world that keep copies of images, JS and CSS close to you. | A local convenience store vs the central warehouse |
| <Term k="database">Database</Term> | Where the real data (products, users, orders) lives on disk. | The pantry / storeroom |
| <Term k="cache">Cache</Term> | A fast, temporary copy of frequently used data. | Ingredients kept on the counter instead of in the basement |

<Callout type="frontend">
You already use most of these every day without thinking about them. `fetch('/api/products')` is the client making a request. The Network tab in DevTools shows the DNS lookup, connection time, TTFB (time to first byte) and download time for every request. In this course you'll learn what happens **on the other side** of that request.
</Callout>

## Zooming in: the timeline of one request

Each step costs time. Here is a rough timeline for a first visit (numbers vary a lot):

| Step | Typical time | Covered in |
|---|---|---|
| DNS lookup | 0–100 ms (0 if cached) | IP, Ports & DNS |
| TCP handshake | 1 round trip (~10–100 ms) | TCP vs UDP |
| TLS handshake | 1–2 round trips | HTTP & HTTPS |
| Server processing | 5–200 ms | Caching, Databases |
| Download response | depends on size & bandwidth | Latency & Bandwidth |
| Static assets | fast if served by a CDN | CDN |

<Callout type="analogy">
Ordering food delivery: you look up the restaurant's address (DNS), call them and confirm who you are (TCP + TLS handshakes), a host sends your order to a free cook (load balancer), the cook grabs ready ingredients from the counter (cache) or from the storeroom (database), and the food is delivered back to you (response). Drinks come from the shop next door because it's faster (CDN).
</Callout>

## Why does this matter for system design?

Everything you just saw works fine for **one** user. System design asks: **what happens with 10 million users?**

- What if the DNS server goes down? → **redundancy**
- What if one server can't handle the traffic? → **horizontal scaling + load balancing**
- What if the database is too slow? → **caching, indexes, replication**
- What if the data is too big for one database? → **sharding**
- What if users are on the other side of the planet? → **CDNs and multiple regions**
- What if a server crashes in the middle of a request? → **fault tolerance, retries**

Each question is a lesson in this course. By the end you'll be able to draw this diagram for any product and **defend every box in it**.

<Callout type="interview">
“What happens when you type a URL?” is sometimes asked as-is, especially for frontend roles. A strong answer goes in order: **DNS → TCP → TLS → HTTP request → load balancer → server → cache/DB → response → rendering**, and mentions caching at each level (browser cache, DNS cache, CDN, server cache). Mention the parts you know well (rendering!) in more depth. That's where you can shine as a frontend dev.
</Callout>

<Takeaways>
- A request is a journey: **name lookup → connect → send → process → respond → render**.
- Big systems are made of a few repeating building blocks: **clients, DNS, load balancers, servers, caches, databases, CDNs**.
- System design is about making this journey **fast, reliable and scalable** for millions of users.
</Takeaways>
